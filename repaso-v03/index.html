R3 · Punto de partida

Teclea una letra y el programa se vuelve loco


int main() {
    int edad = 0;
    while (edad <= 0) {
        std::cout << "Edad: ";
        std::cin >> edad;
    }
    std::cout << "Gracias\n";
}
      

Edad: veinte
Edad: Edad: Edad: Edad: Edad: Edad: Edad: Edad: Edad: …

El programa dejó de pedir datos y ya no se detiene. No hay error de compilación, ni excepción, ni mensaje.

R3 · Los dos operadores

<< saca datos, >> mete datos


int main() {
    std::string nombre;
    int edad = 0;
    std::cout << "Nombre y edad: ";
    std::cin >> nombre >> edad;
    std::cout << nombre << " tiene " << edad << " anios\n";
}
  • Las flechas apuntan hacia dónde van los datos: cout saca, cin mete.
  • Se encadenan porque cada operación devuelve el flujo.
  • '\n' salta de línea. std::endl además vacía el búfer de salida, lo que es más lento; úsalo solo cuando necesites ver la salida de inmediato.
R3 · El búfer de entrada

>> se detiene en el primer espacio

Lo que tecleas llega a un búfer y se queda ahí hasta que alguien lo consume.


Tecleas:   Ana 20⏎
Búfer:     A n a ␣ 2 0 ⏎

cin >> nombre;   salta espacios, toma "Ana", deja  ␣ 2 0 ⏎
cin >> edad;     salta el espacio, toma 20,  deja  ⏎
  • >> descarta los espacios, tabuladores y saltos de línea que encuentra antes del dato.
  • Se detiene en el primer separador que aparece después, y lo deja intacto en el búfer.
Checkpoint

Con std::string s; std::cin >> s; el usuario teclea Ana Maria Perez y presiona Enter. ¿Qué queda en s?

C. >> lee hasta el primer espacio en blanco, así que toma Ana y deja ␣Maria␣Perez⏎ en el búfer para la siguiente lectura. Para capturar la línea entera hace falta getline (A). La lectura no falla: leer una palabra es un éxito (B).
R3 · getline

Leer una línea completa, espacios incluidos


int main() {
    std::string linea;
    std::cout << "Frase: ";
    std::getline(std::cin, linea);
    std::cout << "[" << linea << "] mide "
              << linea.size() << '\n';
}
  • Lee hasta el siguiente '\n', sin saltar espacios iniciales.
  • Consume ese '\n' y no lo guarda: el búfer queda limpio hasta el siguiente Enter.
  • Es función libre: std::getline(std::cin, s), no cin.getline(s).
R3 · El choque clásico

>> seguido de getline devuelve vacío


int edad = 0;
std::string nombre;
std::cout << "Edad: ";
std::cin >> edad;                    // deja el ⏎ en el búfer
std::cout << "Nombre completo: ";
std::getline(std::cin, nombre);      // encuentra ese ⏎ de inmediato
std::cout << "[" << nombre << "]\n";
      

Edad: 20⏎
Nombre completo: []          <- ni siquiera esperó a que tecleara

>> tomó los dígitos y dejó el '\n' sin consumir. getline leyó desde ahí, encontró el fin de línea en la posición cero y devolvió una cadena vacía, correctamente y sin fallar.

R3 · El choque clásico

Descartar lo que quedó con ignore


#include <limits>
int edad = 0;
std::string nombre;
std::cout << "Edad: ";
std::cin >> edad;
std::cin.ignore(
    std::numeric_limits<std::streamsize>::max(), '\n');
std::getline(std::cin, nombre);      // ahora sí espera
  • ignore(n, c) descarta hasta consumir n o hallar c, incluido el propio c.
  • std::numeric_limits<std::streamsize>::max() es el mayor valor del tipo que cuenta caracteres: "sin límite práctico". Vive en <limits>.
  • cin.ignore() sin argumentos descarta un solo carácter. Alcanza para este caso y falla si el usuario tecleó 20 basura⏎.
Checkpoint

Un programa hace cin >> n; y luego dos getline seguidos. El usuario teclea 5⏎, rojo⏎, azul⏎. Sin ningún ignore, ¿qué guardan las dos cadenas?

A. El '\n' que dejó >> es lo primero que encuentra el primer getline, que devuelve vacío. Todo se recorre una posición: el segundo getline recoge "rojo" y "azul" se queda esperando. B es lo que ocurriría con el ignore puesto. El flujo no falla en ningún momento (C): leer una línea vacía es una lectura válida.
R3 · Estados del flujo

Por qué el ciclo del arranque no termina

Con veinte donde cin >> edad esperaba dígitos pasan tres cosas:

  1. edad se queda como estaba. Desde C++11 se le asigna 0; en ningún caso recibe el texto.
  2. El flujo enciende su bandera de fallo y cin.fail() pasa a valer true.
  3. Los caracteres veinte⏎ siguen en el búfer, sin consumir.

La siguiente vuelta vuelve a leer, falla igual y deja el búfer intacto. Mientras el flujo esté en fallo, toda lectura posterior no hace nada.

Cuatro estados: good, fail (formato equivocado), eof (entrada agotada) y bad (irrecuperable).

R3 · Recuperación

clear() primero, ignore() después


std::cout << "Numero: ";
if (!(std::cin >> n)) {                  // la lectura falló
    std::cout << "Eso no es un numero\n";
    std::cin.clear();                    // 1) apaga la bandera
    std::cin.ignore(                     // 2) tira la basura
        std::numeric_limits<std::streamsize>::max(), '\n');
}
  • clear() vuelve a good, pero no toca el búfer.
  • ignore() descarta la línea, pero con la bandera encendida no consume nada.
El orden importa. Primero clear(), después ignore(). Al revés no limpia nada.
Checkpoint

Dentro de un ciclo que relee hasta obtener un número, un compañero puso solo std::cin.clear(); tras detectar el fallo. ¿Qué pasa al teclear abc?

B. clear() solo modifica las banderas de estado; no toca los caracteres pendientes. Con el flujo en good y abc todavía ahí, la siguiente lectura falla de nuevo y el ciclo gira igual que antes. Hace falta ignore() para descartar la línea (A). Los flujos no lanzan excepciones salvo que se les active explícitamente (C).
R3 · Lectura validada

El patrón completo, en una función


void limpiarLinea() {
    std::cin.clear();
    std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
}
int leerEntero(const std::string& msg) {
    int n = 0;
    while (true) {
        std::cout << msg;
        bool ok = static_cast<bool>(std::cin >> n);
        limpiarLinea();
        if (ok) return n;
        std::cout << "Entrada invalida.\n";
    }
}

El flujo se convierte a bool, y por eso la lectura sirve como condición.

Limpiar en los dos caminos evita que 20 basura contamine la siguiente lectura.

Checkpoint

El programa pide un entero y el usuario teclea 12abc seguido de Enter. Con std::cin >> n;, ¿qué ocurre?

C. >> consume los caracteres que forman un entero válido y se detiene en el primero que no lo es. Como leyó al menos un dígito, la lectura es un éxito y el flujo sigue en good. Nada se descarta solo (B): abc⏎ espera y hará fallar la siguiente lectura numérica. Por eso el patrón del slide 14 llama a ignore incluso cuando todo salió bien.
R3 · Trampas comunes

Cinco formas de quedarse atorado

  • No revisar el resultado de la lectura. Sin if (cin >> n) el programa sigue con una variable que nunca se llenó.
  • clear() sin ignore(). Es la causa exacta del ciclo infinito que la mayoría no logra explicar.
  • ignore() antes de clear(). Con la bandera encendida ignore no consume nada, así que el orden invertido no limpia.
  • Mezclar >> y getline sin limpiar. La primera línea leída sale vacía.
  • Olvidar #include <limits>. El error apunta a numeric_limits y no menciona la cabecera.
R3 · Ejercicio

Un entero entre 1 y 100, pase lo que pase

Escribe leerEnRango(msg, lo, hi) que insista hasta obtener un entero dentro del rango. Pruébala con abc, con 500, con 3.7, con una línea vacía y con 42 basura.


int leerEnRango(const std::string& msg, int lo, int hi) {
    int n = 0;
    while (true) {
        std::cout << msg;
        bool ok = static_cast<bool>(std::cin >> n);
        std::cin.clear();
        std::cin.ignore(
            std::numeric_limits<std::streamsize>::max(), '\n');
        if (ok && n >= lo && n <= hi) return n;
        std::cout << "Escribe un entero entre "
                  << lo << " y " << hi << ".\n";
    }
}

Guardar el resultado en ok permite limpiar el flujo una sola vez, en los dos caminos. Con 3.7 lee 3 y descarta .7: si eso debe rechazarse, hay que leer la línea con getline y validarla completa.
