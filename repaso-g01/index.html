G1 · Punto de partida

La carpeta que ya conoces


$ ls
arreglo.cpp        arreglo_bueno.cpp        arreglo_final.cpp
arreglo2.cpp       arreglo_final_ESTE_SI.cpp

Ninguno de esos nombres dice qué cambió respecto al anterior ni cuándo se cambió. Para saber cuál compila hay que compilarlos todos, y para saber qué le hiciste al que sí compilaba hay que leerlos línea por línea.

Git guarda esa información por ti: qué archivos cambiaron, qué líneas, en qué momento y con qué descripción.

G1 · Modelo mental

Tres áreas, dos comandos

git add copia el contenido actual del archivo al staging. git commit guarda lo que haya en el staging como un punto de la historia, un commit. La flecha de regreso es git restore, que copia el staging sobre el archivo del disco: el comando del slide 14.

G1 · Configuración

Cuatro líneas, una sola vez por computadora


git config --global user.name "Tu Nombre"
git config --global user.email "a01234567@tec.mx"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"

Las cuatro quedan escritas en ~/.gitconfig y aplican a todos tus repositorios. El nombre y el correo se graban dentro de cada commit.

Sin core.editor, un git commit sin -m abre el editor que traiga el sistema: nano en Linux y WSL, vim en macOS. Si no reconoces la pantalla, el slide de trampas tiene la salida de emergencia de cada uno.

$ mkdir repaso-cpp && cd repaso-cpp

Con init.defaultBranch main configurado, git imprime solo la última línea. Esa línea anuncia la carpeta oculta .git/, donde vive la historia.

Checkpoint

Ejecutas git add main.cpp, cierras la terminal y apagas la computadora. ¿Qué quedó registrado en la historia del repositorio?

B. El staging es la lista de lo que entrará al próximo commit, y la historia solo cambia cuando corres git commit. A confunde el staging con el repositorio. C agrega un error más: nada sale de tu computadora sin git push, y en este punto ni siquiera existe un repositorio remoto.

G1 · Qué ve git

git status antes del primer commit


$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	r00-compilacion/

nothing added to commit but untracked files present [...]

Untracked significa que git ve el archivo y todavía no lo sigue. Este comando dice en qué rama estás y qué cambió desde el último commit.

G1 · Guardar

Del disco al staging, del staging a la historia


$ git add .
$ git status --short
A  .gitignore
A  r00-compilacion/main.cpp

$ git commit -m "R0: compilacion desde la terminal"
[main (root-commit) 6050ad0] R0: compilacion desde la terminal
 2 files changed, 12 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 r00-compilacion/main.cpp

El binario programa está en la carpeta y no aparece en ninguna de las dos salidas: el .gitignore lo dejó fuera. 6050ad0 es el identificador del commit.

G1 · La historia

git log --oneline se lee como una lista


$ git log --oneline
650683f R11: ejercicio de la sesion
ed4156c R10: ejercicio de la sesion
cf91ed7 R9: ejercicio de la sesion
203e666 R8: ejercicio de la sesion
b5cee31 R7: ejercicio de la sesion
6f3feea R6: ejercicio de la sesion

Cada línea es un commit: identificador y mensaje. Esta historia lleva seis sesiones guardadas.

Sirven: qué se hizo, en una línea, sin punto final.

  • R5: arreglo dinamico con destructor
  • R8: corrige el indice fuera de rango

No sirven: no dicen qué cambió.

  • cambios
  • asdf
  • arreglé cosas
Checkpoint

Commiteaste el binario programa por error. Después agregas la línea programa a tu .gitignore y vuelves a commitear. ¿Qué pasa con el binario?

C. Un archivo que ya entró a un commit queda bajo seguimiento y sus cambios aparecen en git status aunque su nombre esté en el .gitignore. Para sacarlo hay que ejecutar git rm --cached programa y commitear esa eliminación. A es falso: .gitignore nunca borra archivos del disco. B también: los commits viejos no cambian, el binario sigue en ellos.

La línea con - es la del último commit y la del + es la que tienes ahora.

G1 · Deshacer

Volver al último estado que compilaba


$ git status --short
 M r00-compilacion/main.cpp

$ git restore r00-compilacion/main.cpp

$ git status --short

git restore no imprime nada y git status --short queda vacío: el archivo volvió al contenido que tenía en el staging y el programa compila otra vez. Como no habías hecho git add, el staging todavía guardaba lo del último commit, así que el archivo quedó como en HEAD.

Los cambios que descarta git restore no estaban en ningún commit y no se recuperan. Commitear cuando algo funciona es lo que hace barata esta operación.
G1 · Deshacer

Las dos columnas de git status --short


# tras editar main.cpp otra vez
$ git add r00-compilacion/main.cpp
$ git status --short
M  r00-compilacion/main.cpp     <- primera columna: staging

$ git restore --staged r00-compilacion/main.cpp
$ git status --short
 M r00-compilacion/main.cpp     <- segunda columna: disco

La primera columna describe el staging y la segunda el directorio de trabajo. git restore --staged saca el archivo del staging y deja el contenido del disco intacto; git restore sin bandera sobrescribe el archivo del disco con lo que haya en el staging.

Si ya hiciste git add de una versión rota y quieres volver al último commit, hacen falta los dos: git restore --staged archivo y después git restore archivo. En un solo comando, git restore --source=HEAD --staged --worktree archivo.

Checkpoint

Modificaste main.cpp, no has hecho commit y ejecutas git restore main.cpp. ¿Qué le pasó a la historia del repositorio?

B. git restore copia sobre el archivo lo que hay en el staging, que aquí coincide con el último commit, y no toca los commits. A describe un comando que borra historia, que no es este. C describe git revert, que sí crea un commit nuevo para deshacer uno anterior y se usa cuando el cambio ya estaba guardado.
G1 · Publicar

Una copia fuera de tu computadora

  • Crea tu cuenta en github.com con un correo al que tengas acceso permanente.
  • Instala GitHub CLI: brew install gh en macOS, sudo apt install gh en Linux o WSL.

gh auth login    # GitHub.com, HTTPS, "Login with a web browser"
gh repo create repaso-cpp --public --source . --push

gh auth login imprime un código corto y te pide pegarlo en el navegador. --source . publica el repositorio local que ya está en esa carpeta, --push sube los commits y gh imprime la dirección del repositorio remoto.

G1 · Publicar

Los días siguientes: git push


$ git push
To https://github.com/USUARIO/repaso-cpp.git
   4f155c6..34197bb  main -> main

$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

Los dos identificadores son el último commit que tenía GitHub y el que tiene ahora. Si creas el repositorio desde la página en vez de con gh, la primera vez se usa git push -u origin main y git responde * [new branch] main -> main.

Checkpoint

Trabajaste toda la tarde, hiciste git add y git commit tres veces, no ejecutaste git push y tu disco duro deja de funcionar. ¿Qué hay en GitHub?

A. git commit escribe en la carpeta .git/ de tu máquina y no usa la red. B supone que commit y push son lo mismo. C ignora que el remoto ya existía con los commits del último push; esos no se pierden.
G1 · Trampas comunes

Cuatro maneras de complicarte

  • Commitear binarios: quitarlos después exige git rm --cached y siguen pesando en los commits viejos. Por eso el .gitignore va en el primero.
  • Escribir git add . sin leer antes git status.
  • Ejecutar git commit sin -m y caer en un editor desconocido.
  • Creer que git push respalda el trabajo del día. Envía commits; lo que no commiteaste se queda en tu máquina.

$ git commit
# Please enter the commit message for your changes. Lines starting
# with '#' will be ignored, and an empty message aborts the commit.

   nano (Linux, WSL):  Ctrl+X
   vim  (macOS):       Esc  luego  :q!  y Enter

Aborting commit due to empty commit message.

Para saber cuál te va a abrir: git var GIT_EDITOR.

G1 · Ejercicio

Arma el repositorio de la serie


repaso-cpp/
├── .gitignore
├── README.md
├── r00-compilacion/
├── r01-vscode/
└── …   una carpeta por sesión, hasta r19-stl/
  1. Crea el repositorio y mueve ahí lo que escribiste en R0 y en R1.
  2. Haz dos commits separados, uno por sesión, con el .gitignore en el primero.
  3. Publícalo en GitHub con gh y revísalo en el navegador.

mkdir repaso-cpp && cd repaso-cpp
git init
# crea .gitignore, README.md, r00-compilacion/ y r01-vscode/
git add .gitignore README.md r00-compilacion
git commit -m "R0: compilacion desde la terminal"
git add r01-vscode
git commit -m "R1: tareas de compilacion en VS Code"
git log --oneline
gh repo create repaso-cpp --public --source . --push

El .gitignore, el README.md y un script que crea las veinte carpetas están en la plantilla del repositorio. Nombrar los archivos en git add en vez de usar . es lo que permite separar los dos commits.
