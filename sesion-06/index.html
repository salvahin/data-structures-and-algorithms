4.1 Búsqueda secuencial

4.1 · Búsqueda secuencial

El algoritmo que ya conocen


template <typename T>
int busquedaSecuencial(const std::vector<T>& a, const T& x) {
    for (int i = 0; i < (int)a.size(); ++i) {
        if (a[i] == x) return i;
    }
    return -1;   // no está
}
  • Funciona sobre cualquier secuencia, ordenada o no. Solo exige que T admita ==.
  • Recorre de izquierda a derecha y se detiene en la primera coincidencia.
4.1 · Búsqueda secuencial

Análisis de casos

CasoComparacionesCuándo ocurre
Mejor1x está en la primera posición
Peornx está al final o no está
Promedio(n+1)/2x está, en posición uniforme al azar

Los tres casos crecen linealmente con n (la constante ½ no cambia el orden): la búsqueda secuencial es O(n) y también Ω(n) en el peor caso.

Checkpoint

En promedio, la búsqueda secuencial encuentra x a la mitad del arreglo. ¿Qué complejidad tiene el caso promedio?

C. n/2 es una función lineal: la constante ½ desaparece en la notación O y el caso promedio queda en O(n). La opción B confunde "revisar la mitad" con "descartar la mitad en cada paso" — eso solo lo hace la búsqueda binaria, y requiere orden previo.

4.2 Búsqueda binaria

4.2 · Búsqueda binaria

Descartar la mitad en cada paso

  • Precondición: el arreglo está ordenado. Sin esa condición el algoritmo devuelve basura sin avisar.
  • Comparar x con el elemento de en medio decide en qué mitad puede estar, y la otra mitad se descarta completa.
  • Cada comparación reduce el intervalo de búsqueda a la mitad: de n a n/2, a n/4, … a 1.

Toda la corrección del algoritmo descansa en una sola frase: si x está, está en a[lo..hi].

4.2 · Búsqueda binaria

Codificación cuidadosa


int busquedaBinaria(const std::vector<int>& a, int x) {
    int lo = 0, hi = (int)a.size() - 1;
    while (lo <= hi) {                    // intervalo no vacío
        int mid = lo + (hi - lo) / 2;     // punto medio seguro
        if (a[mid] == x)      return mid;
        else if (a[mid] < x)  lo = mid + 1;
        else                  hi = mid - 1;
    }
    return -1;   // el intervalo quedó vacío: x no está
}

Cada detalle está ahí por una razón: <= en la condición, +1 y -1 en las actualizaciones, y la forma del punto medio. Los tres son fuente clásica de errores.

4.2 · Búsqueda binaria

El invariante en acción: buscar 37

4.2 · Búsqueda binaria

El invariante demuestra la corrección

Invariante: al inicio de cada iteración, si x está en el arreglo, entonces está en a[lo..hi].

  • Al entrar: lo = 0, hi = n−1 cubre todo el arreglo.
  • Se preserva: si a[mid] < x, el orden garantiza que x no está en a[lo..mid], y [mid+1, hi] mantiene la propiedad. Simétrico en el otro caso.
  • Al salir: lo > hi significa intervalo vacío; por el invariante, x no está. Devolver −1 es correcto.
  • Termina: cada iteración descarta al menos un elemento.
4.2 · Búsqueda binaria

El bug clásico del punto medio


int mid = (lo + hi) / 2;        // desborda si lo + hi > INT_MAX
                                // (comportamiento indefinido en C++)

int mid = lo + (hi - lo) / 2;   // hi - lo siempre cabe en int
                                // mismo resultado, sin desbordamiento
  • Con arreglos de más de ~2³⁰ elementos, lo + hi puede exceder INT_MAX: desbordamiento de entero con signo.
  • Este bug vivió casi una década en java.util.Arrays.binarySearch hasta que Joshua Bloch lo documentó en 2006. Código revisado por miles de personas, con pruebas, en producción.
Checkpoint

¿Por qué se escribe mid = lo + (hi - lo) / 2 en lugar de (lo + hi) / 2?

B. Con lo y hi no negativos, hi - lo siempre cabe en int, mientras que lo + hi puede exceder INT_MAX — y el desbordamiento de enteros con signo es comportamiento indefinido en C++. Ambas formas redondean igual (A) y el costo de la operación es idéntico (C).
4.2 · Búsqueda binaria

Demostración de O(log n) vía recurrencia

Cada iteración hace trabajo constante y reduce el problema a la mitad:

T(n) = T(n/2) + c

  • Desplegando: T(n) = T(n/4) + 2c = T(n/8) + 3c = … = T(1) + c·log₂n.
  • Teorema Maestro: a=1, b=2, f(n)=Θ(1) → caso 2 → Θ(log n).

4.2 · Búsqueda binaria

Carrera en vivo: n = 1 000 000

Corremos ambas búsquedas sobre el mismo arreglo ordenado, con contador de comparaciones:

  • Búsqueda secuencial: ≈ 500 000 comparaciones en promedio por consulta.
  • Búsqueda binaria: ≤ 20 comparaciones por consulta, siempre.
  • La diferencia crece con n: al duplicar el arreglo, la secuencial duplica su trabajo y la binaria suma una comparación.
Checkpoint

Un arreglo ordenado tiene 10⁹ elementos. ¿Cuántas comparaciones hace la búsqueda binaria en el peor caso?

A. El peor caso es ⌈log₂(10⁹)⌉ ≈ 30: cada comparación reduce el intervalo a la mitad, y 2³⁰ ≈ 10⁹. La opción B describe el caso promedio de la búsqueda secuencial; la C no corresponde a ningún algoritmo de esta sesión — la intuición de "raíz de n" no aparece aquí.

4.3 El costo oculto:
ordenar no es gratis

4.3 · ¿Cuándo compensa ordenar?

El punto de equilibrio

La búsqueda binaria exige un arreglo ordenado, y ordenar cuesta O(n log n). Con k consultas sobre los mismos datos:

EstrategiaCosto total
k búsquedas secuencialesO(k · n)
Ordenar una vez + k búsquedas binariasO(n log n + k · log n)
  • Igualando ambos costos: ordenar compensa aproximadamente cuando k > log n.
  • Con n = 10⁶: si vas a consultar más de ~20 veces, ordena primero. Con una sola consulta, la secuencial gana.
4.3 · ¿Cuándo compensa ordenar?

El criterio de decisión

  • Una consulta, datos desordenados: búsqueda secuencial. Ordenar para buscar una vez tira n log n de trabajo.
  • Muchas consultas, datos estables: ordenar una vez y amortizar el costo entre todas las búsquedas binarias.
  • Consultas mezcladas con inserciones: mantener el orden cuesta O(n) por inserción — ninguna de las dos opciones es buena. Ese problema lo resuelven los árboles de búsqueda del bloque 3.

El mismo razonamiento — costo de preparación contra costo por consulta — reaparece con tablas hash e índices de bases de datos.

4.4 Búsqueda binaria
sobre la respuesta

4.4 · Búsqueda sobre la respuesta

El patrón: buscar en el espacio de respuestas

  • Hay problemas donde no buscas un elemento en un arreglo, sino el menor valor que cumple una condición: la capacidad mínima, la velocidad mínima, el tiempo mínimo.
  • Si el predicado factible(c) es monótono — falso, falso, …, falso, verdadero, verdadero, … — el espacio de respuestas se comporta como un arreglo ordenado de booleanos.
  • Y sobre eso se puede hacer búsqueda binaria: encontrar la frontera donde el predicado cambia de falso a verdadero.
4.4 · Búsqueda sobre la respuesta

La plantilla del patrón


// menor c en [lo, hi] tal que factible(c) es verdadero
long lo = 1, hi = cotaSuperior;
while (lo < hi) {
    long mid = lo + (hi - lo) / 2;
    if (factible(mid)) hi = mid;      // mid podría ser la respuesta
    else               lo = mid + 1;  // mid no alcanza: descártalo
}
// aquí lo == hi: la primera c factible
return lo;
  • Nota la variante: hi = mid (no mid − 1), porque mid factible sigue siendo candidato.
  • Costo: O(log(rango) · costo de factible). El trabajo duro es demostrar la monotonía.
Checkpoint

¿Qué condición debe cumplir el predicado factible(c) para poder aplicar búsqueda binaria sobre la respuesta?

C. La monotonía es lo que convierte el espacio de respuestas en una secuencia F…FV…V donde tiene sentido buscar la frontera. El costo de factible puede ser O(n) sin problema (A) — solo multiplica el log. Y no se ordena ningún arreglo (B): el "orden" ya existe en el espacio de respuestas.
Por qué importa hoy

Por qué un RAG no puede usar búsqueda binaria

  • La búsqueda semántica de un sistema RAG compara embeddings: vectores de 768 o 1536 dimensiones.
  • En una dimensión, "ordenado" y "cercano" coinciden: los vecinos de un valor están junto a él en el arreglo. Eso es lo que la búsqueda binaria explota.
  • En 1536 dimensiones sí se puede imponer un orden total (lexicográfico, orden de Morton), pero ninguno compatible con la proximidad: dos vectores cercanos pueden quedar en extremos opuestos del orden.
  • Por eso existen los índices de búsqueda aproximada — HNSW, IVF — que cambian exactitud por velocidad.

Cierre STL

La trampa: O(log n) exige acceso aleatorio


std::vector<int> v = { /* ordenado */ };
auto it = std::lower_bound(v.begin(), v.end(), x);   // O(log n)
if (it != v.end() && *it == x) { /* está */ }

std::list<int> l = { /* ordenado */ };
auto it2 = std::lower_bound(l.begin(), l.end(), x);  // ¡compila!
// pero avanza el iterador paso a paso: O(n)
  • Los iteradores de std::list no son de acceso aleatorio: llegar al punto medio cuesta n/2 pasos.
  • lower_bound sobre una lista hace O(log n) comparaciones pero O(n) movimientos de iterador. Compila, corre y es lento.
