7.1 Listas encadenadas

7.1 · Listas encadenadas

El modelo: nodos enlazados por punteros


struct Nodo {
    int   dato;
    Nodo* next;    // direccion del siguiente nodo, o nullptr
    Nodo(int d) { dato = d; next = nullptr; }   // nace sin siguiente
};

Nodo* head;        // la lista completa se alcanza desde aqui
// lista vacia: head == nullptr
  • Cada nodo vive en el heap, en una dirección arbitraria; el orden lógico lo dan los enlaces, no la posición en memoria.
  • Insertar y eliminar consiste en reasignar punteros; ningún elemento se desplaza.
7.1 · Listas encadenadas

El operador ->: de dónde viene


Nodo n(7);
Nodo* p = &n;

n.dato;       // objeto: se usa el punto
(*p).dato;    // puntero: primero *, despues el punto
*p.dato;      // error: se lee como *(p.dato)
p->dato;      // abreviatura de (*p).dato
  • El punto tiene mayor precedencia que *; sin paréntesis, *p.dato intenta aplicar el punto a un puntero y no compila.
  • C introdujo -> para no escribir (*p). cada vez que se accede a un campo por medio de un puntero. C++ lo heredó sin cambios.
7.1 · Listas encadenadas

Encadenar flechas: un salto por cada ->

  • Se lee de izquierda a derecha: cada -> sigue un puntero hasta el nodo al que apunta.
  • Si un puntero del camino vale nullptr, la flecha que sigue es comportamiento indefinido. Antes de escribir p->next->dato hay que saber que p y p->next no son nullptr.
Checkpoint

Si p es un Nodo*, ¿qué expresión es equivalente a p->next->dato?

A. Cada -> se traduce a (*…).: p->next es (*p).next, que es otro puntero, y para leer su dato hay que desreferenciarlo también. En la B, (*p).next es un Nodo* y el punto no se aplica a punteros. La C no compila: el punto se aplica antes que el *.

Diseño · La interfaz primero

Las decisiones se toman antes del primer new

  • Operaciones: qué expone la lista y qué devuelve cada operación.
  • Invariantes: qué es cierto entre operación y operación (p. ej. size coincide con el número de nodos).
  • Casos límite: qué hace cada operación con la lista vacía, con un solo elemento, al eliminar la cabeza, con una posición fuera de rango.

Cada caso límite necesita una respuesta decidida y escrita — devolver false, lanzar excepción, o documentar una precondición. Lo que no se decide aquí aparece después como comportamiento accidental.

Diseño · La interfaz primero

El contrato que implementaremos


LinkedList<T>
  insert(x, pos)  post: x queda en la posicion pos;
                  false si pos no esta entre 0 y size
  remove(x)       post: devuelve true si elimino la
                  primera aparicion; false si no estaba
  find(x)         post: posicion de x, o -1
  size()          post: numero de elementos, en O(1)
  print()         post: muestra los datos en orden; no modifica nada
  invariantes: size == numero de nodos; el ultimo -> nullptr

size() en O(1) obliga a mantener un contador y a actualizarlo en cada inserción y eliminación: la garantía de complejidad también es parte del contrato.

Implementación · Esqueleto

Nodo interno y estado de la lista


template <typename T>
class LinkedList {
    struct Nodo {                 // privado: el usuario no ve nodos
        T     dato;
        Nodo* next;
        Nodo(T d) { dato = d; next = nullptr; }
    };
    Nodo* head;                   // primer nodo, o nullptr
    int   count;                  // numero de nodos

public:
    LinkedList() { head = nullptr; count = 0; }   // lista vacia
    ~LinkedList();                // hoy lo escribimos con cuidado
    int size() { return count; }
};

Nodo es un detalle de implementación: va dentro de la clase, privado. La interfaz habla de valores y posiciones, no de punteros.

Implementación · insert

insert completo: validar y la cabeza


bool insert(T x, int pos) {
    if (pos < 0 || pos > count) return false;   // posicion invalida
    Nodo* nuevo = new Nodo(x);
    if (pos == 0) {               // caso especial: nueva cabeza
        nuevo->next = head;
        head = nuevo;
    } else {                      // caso general: el de la animacion
        Nodo* prev = head;
        for (int i = 0; i < pos - 1; i++)
            prev = prev->next;
        nuevo->next = prev->next;
        prev->next = nuevo;
    }
    count++;
    return true;
}

Implementación · remove

remove completo


bool remove(T x) {
    if (head == nullptr) return false;           // lista vacia
    if (head->dato == x) {                       // x es la cabeza
        Nodo* victima = head;
        head = head->next;
        delete victima;
        count--;
        return true;
    }
    Nodo* prev = head;                           // caso general:
    while (prev->next != nullptr && prev->next->dato != x)
        prev = prev->next;
    if (prev->next == nullptr) return false;     // x no estaba
    Nodo* victima = prev->next;
    prev->next = victima->next;
    delete victima;
    count--;
    return true;
}
Checkpoint

Para eliminar el nodo que sigue a prev, un compañero escribe: delete prev->next; prev->next = prev->next->next;. ¿Qué está mal?

A. Tras el delete, prev->next es un puntero colgante y leerle ->next es comportamiento indefinido — puede "funcionar" en la máquina de pruebas y fallar en otra. El orden sí importa (descarta B); los nodos siguientes se conservan al puentear, no hay que liberarlos (descarta C).

Implementación · Destructor

El destructor, en código


~LinkedList() {
    Nodo* actual = head;
    while (actual != nullptr) {
        Nodo* sig = actual->next;   // guardar ANTES de liberar
        delete actual;
        actual = sig;
    }
}
  • Sin destructor, cada lista que sale de scope fuga todos sus nodos — el programa "funciona" y la memoria crece.
  • Se verifica con AddressSanitizer o Valgrind; la sesión 13 lo trabaja a fondo.
Checkpoint

Un destructor hace: while (head != nullptr) { delete head; head = head->next; }. ¿Cuál es el diagnóstico?

C. Tras delete head, leer head->next accede a memoria liberada. Muchas veces el valor "sigue ahí" y el ciclo completa — por eso la opción A es la trampa: describe lo que parece pasar, no lo que garantiza el lenguaje. AddressSanitizer lo reporta a la primera; a ojo, casi nadie lo ve.

Por qué importa hoy

El destructor que la IA no te garantiza

  • Un asistente de IA produce una LinkedList plausible en segundos — y la fuga o el use-after-free aparecen en el caso límite que nadie pidió en el prompt.
  • Detectarlo exige saber exactamente qué debe hacer el destructor y en qué orden: el criterio que estamos construyendo hoy a mano.
  • Ese criterio es el mismo que se usa para revisar código de un compañero, de un tercero o de un modelo — la revisión es el trabajo que no se delega.

Por eso en el curso puedes usar asistentes y debes poder explicar y defender cada línea que entregas.

Por qué importa hoy

Por qué existe .contiguous() en PyTorch

  • Un tensor de PyTorch es una vista sobre un storage: un bloque contiguo de memoria, más strides que dicen cuántos elementos saltar por dimensión.
  • transpose no mueve datos: solo intercambia strides. La vista deja de ser contigua y el recorrido salta por la memoria — el mismo patrón de accesos de una lista encadenada.
  • .contiguous() copia los datos a un bloque nuevo en el orden de la vista. Cuesta una copia completa, y se paga porque los kernels sobre memoria contigua son mucho más rápidos.

En memoria contigua, cada carga de caché trae varios elementos a la vez.
