R13 · new y delete

Dos regiones de memoria con reglas distintas


int* p = new int(42);      int* v = new int[10];
delete p;                  delete[] v;
Checkpoint

Una función hace int* v = new int[100]; y termina con return; sin más. ¿Qué pasa con los 400 bytes?

B. Lo que se libera al salir de la función es el puntero v, que ocupa 8 bytes en la pila. El bloque de 400 bytes vive en el montículo y solo desaparece con un delete[] que ya no puede escribirse: se perdió la única dirección que lo alcanzaba. A confunde la vida del puntero con la del bloque. C atribuye al compilador un seguimiento de reservas que no realiza.

R13 · RAII

El constructor adquiere, el destructor libera

La técnica se llama RAII. Consiste en amarrar la vida de un recurso a la vida de un objeto: si el objeto existe, el recurso está reservado; cuando el objeto muere, el destructor lo suelta. Como C++ garantiza que el destructor corre al salir del ámbito, la liberación deja de depender de que alguien se acuerde.


class Arreglo {
    int* datos;
    int n;
public:
    Arreglo(int tam) : datos(new int[tam]), n(tam) {}
    ~Arreglo() { delete[] datos; }
    void set(int i, int v) { datos[i] = v; }
    int get(int i) const { return datos[i]; }
    int tam() const { return n; }
};

Con estas dos líneas, la fuga del slide anterior es imposible: no hay camino de salida de la función que no pase por el destructor.

Checkpoint

¿Por qué RAII resuelve las fugas incluso cuando la función tiene varios return?

A. La garantía del lenguaje es sobre los objetos, no sobre las reservas: al salir del ámbito por cualquier vía se destruyen las variables locales, y el destructor es quien contiene el delete[]. B describe una transformación que el compilador no hace sobre punteros sueltos. C es falso: el montículo persiste mientras el programa viva.
R13 · Copia superficial

Arreglo b = a; copia la dirección, no el bloque

Como Arreglo no define constructor de copia, el compilador genera uno que copia miembro por miembro. Copiar un int* miembro a miembro es copiar la dirección: los dos objetos quedan apuntando al mismo bloque, y los dos destructores lo liberan.

R13 · Copia profunda

Cada objeto con su propio bloque

La copia profunda reserva un bloque nuevo del mismo tamaño y transfiere los valores uno por uno. Cuesta más, y es la única forma de que a y b sean independientes: modificar uno deja de afectar al otro.

Checkpoint

Con la copia superficial en su lugar, ejecutas b.set(0, 99); y luego imprimes a.get(0). ¿Qué sale?

C. La copia superficial duplicó la dirección, así que b.datos y a.datos son el mismo bloque y escribir por uno se ve por el otro. A describe lo que ocurriría con copia profunda. B supone corrupción; el bloque está intacto, el problema es que se comparte. Este síntoma aparece antes que el aborto y suele confundirse con un error de lógica.
R13 · Constructor de copia

El constructor que recibe otro objeto de su clase


Arreglo(const Arreglo& otro) : datos(new int[otro.n]), n(otro.n) {
    for (int i = 0; i < n; ++i) datos[i] = otro.datos[i];
}
  • El parámetro es const Arreglo&. Por referencia porque pasar por valor exigiría una copia, que llamaría a este mismo constructor sin fin; const porque copiar no debe modificar el original.
  • La lista de inicialización reserva el bloque nuevo antes de que empiece el cuerpo, y el ciclo transfiere los valores.
  • Se invoca en tres situaciones: Arreglo b = a;, Arreglo b(a); y cada vez que un Arreglo se pasa a una función o se devuelve por valor.
R13 · Asignación

a = b es un caso distinto: a ya tiene un bloque


Arreglo& operator=(const Arreglo& otro) {
    if (this == &otro) return *this;
    delete[] datos;
    n = otro.n;
    datos = new int[n];
    for (int i = 0; i < n; ++i) datos[i] = otro.datos[i];
    return *this;
}
  • La primera línea protege contra a = a. Sin ella, el delete[] destruiría el bloque del que se va a copiar.
  • Hay que liberar lo viejo antes de reservar lo nuevo; omitirlo deja una fuga en cada asignación.
  • Devolver Arreglo& permite encadenar a = b = c, que es como se comportan los tipos básicos.
Checkpoint

Escribes operator= sin la comprobación if (this == &otro). ¿Cuándo se nota?

B. La autoasignación rara vez se escribe con ese aspecto: aparece como v[i] = v[j] con i == j, o dentro de una función que recibe dos referencias al mismo objeto. El delete[] libera el bloque y, como otro es el mismo objeto, la reserva siguiente reapunta también su puntero: el ciclo termina copiando desde el bloque nuevo, todavía sin inicializar. A subestima el caso indirecto. C generaliza de más: cuando los objetos son distintos, liberar lo viejo es exactamente lo correcto.
R13 · Regla de tres

Si escribes una, escribe las tres

La regla de tres dice que una clase que necesita cualquiera de estas tres funciones casi siempre necesita las otras dos, porque las tres responden a la misma causa: la clase administra un recurso que el compilador no sabe copiar ni liberar.

FunciónCuándo correQué hace con el bloque
~Arreglo()Al morir el objetoLo libera
Arreglo(const Arreglo&)Al crear un objeto a partir de otroReserva uno nuevo y copia
operator=(const Arreglo&)Al asignar sobre un objeto ya construidoLibera el suyo, reserva y copia

R13 · Depuración

Mirar el puntero en el panel de variables

Pon un punto de interrupción antes y después del delete, y observa las dos columnas del panel: la del puntero y la del valor apuntado. En VS Code, expandir un int* muestra la dirección; escribir *p en la sección de expresiones vigiladas muestra el contenido.


p    = 0xc64132b61eb0
*p   = 42
p    = 0xc64132b61eb0   despues de delete p;  (sin cambio)
p    = 0                despues de p = nullptr;
  • delete no modifica el puntero. La variable sigue guardando la misma dirección, ahora de un bloque que ya no te pertenece: un puntero colgante.
  • Leer *p después del delete suele devolver el valor anterior durante un rato, hasta que otra reserva ocupa ese espacio. Por eso el error parece intermitente.
  • Asignar p = nullptr; convierte un error silencioso en una falla inmediata y reproducible.

La salida trae las dos liberaciones: la que falla y la que ocurrió primero, cada una con archivo y línea. Compárala con free(): double free detected in tcache 2, que es todo lo que da el programa sin instrumentar. El costo es un binario dos o tres veces más lento, aceptable para desarrollo.

Checkpoint

Tu programa a veces imprime bien y a veces basura, sin que cambies nada. ¿Cuál es la primera herramienta que usas?

A. Una salida intermitente es la firma de leer memoria que ya no es tuya, y el sanitizer detiene el programa en la primera lectura inválida con archivo y línea. B tarda mucho y además los cout cambian el patrón de reservas, así que el síntoma puede desaparecer. C es útil una vez que sabes dónde mirar, no para localizar el punto de partida.
R13 · Trampas comunes

Cuatro errores que el compilador no detecta

  • Liberar con delete lo reservado con new[]. Compila sin una advertencia y produce alloc-dealloc-mismatch (operator new [] vs operator delete) bajo el sanitizer.
  • No poner el puntero en nullptr después de liberarlo, y llamar delete una segunda vez. Sobre nullptr, delete es una operación válida que no hace nada.
  • Devolver un objeto con memoria propia por valor sin haber escrito el constructor de copia.
  • Escribir el destructor y dar por terminado el trabajo. Sin las otras dos funciones, el destructor correcto es justamente lo que provoca el doble delete.

R13 · Hacia Estructuras de Datos

Una lista encadenada es esta misma clase


struct Nodo {
    int dato;
    Nodo* siguiente;
};

class Lista {
    Nodo* cabeza;
    // reserva cada nodo con new, los enlaza,
    // y el destructor los recorre liberandolos con delete
};
  • Copiar una Lista sin constructor de copia deja dos listas compartiendo los mismos nodos, y el segundo destructor los libera por segunda vez.
  • Lo mismo aplica a los árboles y a los grafos del curso: cambia el número de punteros por nodo, no el problema.
  • Cada estructura que implementes en el semestre lleva su regla de tres. Los errores de esas prácticas serán los de esta sesión.
