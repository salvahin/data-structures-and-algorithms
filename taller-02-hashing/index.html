Objetivo del taller

Al terminar podrás…

  • Implementar una tabla hash con direccionamiento abierto que sí permita borrar.

  • Guardar en un mapa algo que no aparece en la entrada, como una suma acumulada, para responder en orden uno una pregunta sobre el pasado.

Método

Los mismos cinco pasos en los tres problemas

  1. Entender el enunciado con un ejemplo hecho a mano.
  2. Fuerza bruta: la solución más directa, aunque sea lenta, y su costo.
  3. Qué se repite: el trabajo que la fuerza bruta hace una y otra vez.
  4. Qué guardar y con qué clave: la estructura que evita repetir ese trabajo.
  5. Escribir y probar, empezando por los casos borde.

Problema 1
LC 706 · Design HashMap

LC 706 · Enunciado

Una tabla hash propia, sin usar la de la STL

  • Implementar la clase MyHashMap con tres operaciones: put(key, value) guarda o actualiza, get(key) regresa el valor o −1, y remove(key) quita la clave si está.
  • Restricciones: \(0 \le key, value \le 10^{6}\), y a lo más \(10^{4}\) llamadas en total.
  • Ejemplo: put(1, 1), put(2, 2), get(1) → 1, get(3) → −1, put(2, 1), get(2) → 1, remove(2), get(2) → −1.

Fíjate en put(2, 1): la clave 2 ya existía, así que no se agrega otra pareja; se cambia el valor.

¿Puedo usar unordered_map por dentro? El enunciado lo prohíbe, y el juez no lo detecta. Si lo usas, el problema se resuelve en tres líneas y no practicas nada de lo que pide.

LC 706 · Decisión 1

¿Por qué no un arreglo de un millón de casillas?

Arreglo directoTabla hash
Ideavalores[key], una casilla por clave posible\(M\) casillas, la clave elige una con key % M
Memoria\(10^{6} + 1\) enteros, unos 4 MB\(2 \times 20\,011\) enteros, unos 160 KB
Colisionesno hayhay que resolverlas
Si las claves fueran cadenas o enteros de 64 bitsimposiblefunciona igual

Con estas restricciones el arreglo directo pasa las pruebas. La memoria depende del rango de las claves y no de cuántas se guardan; por eso hoy hacemos la tabla hash.

LC 706 · Decisión 2

¿De qué tamaño? \(M = 20\,011\)

  • Con a lo más \(10^{4}\) llamadas, la tabla guarda a lo más \(10^{4}\) claves.
  • Con sondeo lineal conviene \(\alpha \le 0.5\): con la fórmula de la sesión 24, una búsqueda que falla revisa en promedio 2.5 casillas.
  • \(10^{4} / 0.5 = 20\,000\) casillas, y el primo siguiente es \(20\,011\). Con \(m\) primo, las claves con patrones se reparten.
\[ \alpha = \frac{10^{4}}{20\,011} \approx 0.5 \]

¿Por qué 0.5, si en la sesión 24 el límite era 0.7? 0.7 es donde el sondeo lineal empieza a ser lento: unas 6 casillas por búsqueda fallida. Aquí la memoria sobra, así que se elige un \(\alpha\) cómodo, con 2.5 casillas.

LC 706 · Decisión 3

¿Encadenamiento o direccionamiento abierto?

  • Encadenamiento borraría quitando un nodo de una lista, como en la sesión 12. Necesita new, delete y un destructor.
  • Direccionamiento abierto usa dos arreglos de tamaño fijo y no pide memoria dinámica. Su problema es borrar.
  • Elegimos direccionamiento abierto con sondeo lineal, porque obliga a resolver el borrado con lápidas, el punto que quedó pendiente en la sesión 24.

Una casilla puede estar en tres estados: con una clave, VACIA (nunca se usó) o BORRADA (tuvo una clave que ya se quitó).

LC 706 · Escribir el código

Las constantes, los datos y el constructor

const int M = 20011;
const int VACIA = -1;
const int BORRADA = -2;
class MyHashMap {
int claves[M];
int valores[M];
public:
MyHashMap() {
for (int i = 0; i < M; i++)
claves[i] = VACIA;
}
// buscar, put, get y remove
};
Ya están tomadas tres decisiones: un arreglo de tamaño fijo \(M\) primo, sondeo lineal y lápidas para borrar. Ahora se escriben, una por una.
El tamaño. \(M\) es constante para poder declarar arreglos de ese tamaño dentro de la clase.
Dos marcas. Las claves van de 0 a \(10^{6}\), así que ningún valor negativo puede ser una clave. −1 y −2 sirven como marcas sin necesitar un tercer arreglo de estados.
Dos arreglos paralelos. La casilla i guarda una pareja: claves[i] y valores[i]. Es lo mismo que un arreglo de parejas, sin introducir pair.

¿Por qué arreglos y no vector? El tamaño se conoce desde antes de compilar y nunca cambia. Un vector también funcionaría.
Todo empieza vacío. Solo hace falta marcar las claves. Los valores no se inicializan porque solo se leen cuando la clave está.
Faltan las operaciones. Las tres necesitan encontrar dónde está una clave, así que primero se escribe esa búsqueda una sola vez.
LC 706 · Escribir el código

Una función para encontrar la casilla de una clave

int buscar(int key) {
int pos = key % M;
while (claves[pos] != VACIA) {
if (claves[pos] == key)
return pos;
pos = (pos + 1) % M;
}
return -1;
}
put, get y remove empiezan igual: hay que saber si la clave está guardada y en qué casilla.
Qué regresa. La casilla donde está key, o −1 si no está. Con un número se responden las dos preguntas.

¿Debería ser private? Sí, nadie fuera de la clase la necesita. La dejamos pública para no agregar otra sección a la clase.
Dónde empezar. En la casilla que da la función hash. Es la primera que probó la inserción.
Cuándo parar. Solo en una casilla VACIA, nunca en una BORRADA: detrás de una lápida puede estar la clave que buscamos.
La encontró. Se regresa la casilla de inmediato.
La siguiente. El % M regresa a la casilla 0 después de la última, como en la fila circular. Es la misma regla que (k % M + i) % M de la sesión 24, sin llevar la cuenta de i.
No está. Se llegó a una VACIA. El ciclo siempre termina: con \(10^{4}\) claves y \(20\,011\) casillas, siempre quedan casillas vacías.
LC 706 · Escribir el código

put: actualizar si ya está, insertar si no

void put(int key, int value) {
int pos = buscar(key);
if (pos != -1) {
valores[pos] = value;
return;
}
pos = key % M;
while (claves[pos] != VACIA &&
claves[pos] != BORRADA)
pos = (pos + 1) % M;
claves[pos] = key;
valores[pos] = value;
}
Insertar tiene un caso que es fácil olvidar: la clave ya puede estar guardada.
La firma es la que pide LeetCode: no regresa nada.
Primero buscar. Si la clave ya está y se inserta otra vez, la tabla tendría dos parejas con la misma clave, y get podría regresar la vieja.
Ya estaba: se cambia el valor y se termina.
No estaba: se busca lugar desde la casilla inicial.
Un lugar libre es una casilla VACIA o una BORRADA. Este ciclo sí se detiene en las lápidas: aquí ya sabemos que la clave no está, y la lápida se puede reutilizar.

¿No recorre la ruta dos veces? Sí. buscar podría recordar la primera lápida que vio y ahorrarse este ciclo. Lo dejamos en dos ciclos para que cada uno haga una sola cosa.
Se escribe la pareja en la casilla encontrada.
LC 706 · Escribir el código

get y remove se apoyan en buscar

int get(int key) {
int pos = buscar(key);
if (pos == -1)
return -1;
return valores[pos];
}
void remove(int key) {
int pos = buscar(key);
if (pos != -1)
claves[pos] = BORRADA;
}
Con buscar escrita, las dos operaciones que faltan son cortas.
get regresa un entero: el valor, o −1 si la clave no está.
Si no está, el enunciado pide −1. No hay que confundirlo con un valor guardado, porque los valores van de 0 a \(10^{6}\).
Si está, el valor vive en la misma casilla, en el otro arreglo.
remove no regresa nada. Si la clave no está, no hace nada.
Encontrar antes de borrar. Igual que en get.
La lápida. Se escribe BORRADA, no VACIA. Si se escribiera VACIA, las claves que se guardaron después en la misma ruta dejarían de encontrarse. La animación siguiente lo muestra.

LC 706 · Probar

Casos que vale la pena probar antes de enviar

CasoQué revisa

20016 y 40027 dejan residuo 5 al dividirlos entre 20011. Las colisiones no aparecen solas en pruebas al azar; hay que provocarlas.

LC 706 · Costo

Cuánto cuesta cada operación

  • Cada operación hace a lo más dos recorridos cortos de la tabla. Con \(\alpha \approx 0.5\), cuestan orden uno en promedio.
  • La memoria es fija: dos arreglos de \(M\) enteros, se guarde una clave o diez mil.
  • Las lápidas no se convierten de nuevo en VACIA. Con muchos borrados, las búsquedas se alargan; en una tabla de uso general, esa es otra razón para hacer rehash, que limpia las lápidas al reinsertar.
Checkpoint

En MyHashMap, el while de buscar se detiene en VACIA pero no en BORRADA. ¿Por qué?

C. La lápida ocupa un lugar en la ruta de sondeo de otras claves. Si el 17 se borró de la casilla 4 y el 24 se había guardado en la 5 porque la 4 estaba ocupada, buscar el 24 tiene que pasar por la 4. El valor viejo no se lee nunca (A), y las lápidas pueden quedar en cualquier casilla (B).

Problema 2
LC 49 · Group Anagrams

LC 49 · Enunciado

Juntar las palabras que tienen las mismas letras

  • Dada una lista de palabras, agruparlas en anagramas: palabras con exactamente las mismas letras, en otro orden.
  • Entrada: ["eat", "tea", "tan", "ate", "nat", "bat"]
  • Salida, en cualquier orden: [["bat"], ["nat", "tan"], ["ate", "eat", "tea"]]
  • Restricciones: hasta \(10^{4}\) palabras, de hasta 100 letras minúsculas cada una.
LC 49 · Fuerza bruta

Comparar cada palabra con cada grupo

  • Para cada palabra, recorrer los grupos que ya existen y preguntar si es anagrama del primero. Si no encaja en ninguno, abre un grupo nuevo.
  • Saber si dos palabras son anagramas: ordenar las dos y comparar. Con palabras de \(L\) letras cuesta \(L \log L\).
  • Con \(n\) palabras, cada una se compara con hasta \(n\) grupos: del orden de \(n^{2} \cdot L \log L\), unos \(10^{8}\) comparaciones con \(10^{4}\) palabras.

Lo que se repite: la misma palabra se ordena una y otra vez, una vez por cada grupo contra el que se compara.

LC 49 · La idea

Una firma que comparten todos los anagramas

  • Dos palabras son anagramas si y solo si, al ordenar sus letras, quedan iguales: "eat", "tea" y "ate" quedan las tres como "aet".
  • Esa palabra ordenada es una firma del grupo. Se calcula una vez por palabra y sirve como clave en un mapa.
  • Aquí las colisiones se buscan a propósito: todas las palabras de un grupo deben caer en la misma entrada del mapa.

El mapa va de firma a lista de palabras: unordered_map<string, vector<string>>.

LC 49 · Decisión

¿Qué firma usar?

Firma"eat"Costo por palabra¿Correcta?
Suma de los códigos314\(L\)no: "ad" y "bc" también suman 197
Letras ordenadas"aet"\(L \log L\)sí
Conteo de cada letra"1#0#0#0#1#…"\(L + 26\)sí

Usamos las letras ordenadas: es correcta y se escribe en una línea con sort. Con palabras de hasta 100 letras, la diferencia con el conteo es pequeña.

¿Para qué sirve el # en la firma de conteo? Separa los números. Sin él, "1 vez la a y 11 veces la b" y "11 veces la a y 1 vez la b" se escribirían igual, "111", y dos palabras distintas tendrían la misma firma.

LC 49 · Escribir el código

Una pasada por las palabras, otra por el mapa

vector<vector<string>>
groupAnagrams(vector<string>& strs) {
unordered_map<string, vector<string>> grupos;
int n = strs.size();
for (int i = 0; i < n; i++) {
string palabra = strs[i];
string clave = palabra;
sort(clave.begin(), clave.end());
grupos[clave].push_back(palabra);
}
vector<vector<string>> resultado;
for (auto par : grupos)
resultado.push_back(par.second);
return resultado;
}
El plan: calcular la firma de cada palabra y usarla como clave del mapa.
La firma de LeetCode. Recibe la lista por referencia y regresa una lista de listas. La partimos en dos líneas para que quepa.
El mapa: de firma a la lista de palabras que la tienen.
Una vuelta por palabra. Se toma la palabra con un índice, como en los ciclos de siempre.
La firma. Se copia la palabra y se ordena la copia. La palabra original no se toca, porque es la que va en la respuesta.
Agrupar. Si la firma no está en el mapa, grupos[clave] la crea con una lista vacía. Por eso basta una línea, sin preguntar antes si existe.
Armar la respuesta. Cada entrada del mapa es una pareja: par.first es la firma y par.second la lista. Solo nos interesan las listas.

¿Qué es auto? Le pide al compilador que deduzca el tipo. Aquí sería pair<const string, vector<string>>, que es largo de escribir.
Listo. El orden de los grupos no importa, y el de un unordered_map no está definido.
LC 49 · Ejecución

Seis palabras, tres firmas

LC 49 · Costo y pruebas

De \(n^{2}\) comparaciones a una pasada

  • Cada palabra se ordena una vez y hace una consulta al mapa: del orden de \(n \cdot L \log L\), contra \(n^{2} \cdot L \log L\) de la fuerza bruta.
  • La consulta al mapa no es gratis: calcular el hash de una cadena recorre sus \(L\) letras, como el hash polinomial de la sesión 24. Queda dentro del mismo costo.
  • Casos borde: la lista [""] (una palabra vacía forma su propio grupo), una sola palabra, y todas las palabras iguales.
Checkpoint

Alguien propone usar como firma la suma de los códigos de las letras, porque cuesta \(L\) en lugar de \(L \log L\). ¿Qué pasa con ["ad", "bc"]?

A. 'a' + 'd' = 97 + 100 = 197 y 'b' + 'c' = 98 + 99 = 197. Una firma tiene que ser igual para todos los anagramas y distinta para todo lo demás; la suma cumple lo primero pero no lo segundo. Un mapa con clave int sí compila (C), y el problema aparece desde palabras de dos letras (B).

Problema 3
LC 560 · Subarray Sum Equals K

LC 560 · Enunciado

¿Cuántos pedazos seguidos suman exactamente k?

  • Dado un arreglo de enteros nums y un entero k, contar los subarreglos (pedazos contiguos, de al menos un elemento) cuya suma es k.
  • Ejemplo: nums = [1, 2, −2, 2, 1], k = 3 → 4: [1, 2], [1, 2, −2, 2], [2, −2, 2, 1] y [2, 1].
  • Restricciones: hasta \(2 \times 10^{4}\) elementos, y pueden ser negativos.

El ejemplo de LeetCode es [1, 1, 1] con k = 2 → 2. Usamos uno con negativos porque es el que separa las soluciones correctas de las que no.

¿Un subarreglo es lo mismo que un subconjunto? No. Un subarreglo toma elementos seguidos y en su orden: [1, 2] sí lo es, pero [1, 1], con el primero y el último, no.

LC 560 · Fuerza bruta

Probar cada inicio y cada fin


int cuenta = 0;
for (int i = 0; i < n; i++) {        // inicio
    int suma = 0;
    for (int j = i; j < n; j++) {    // fin
        suma = suma + nums[j];
        if (suma == k)
            cuenta++;
    }
}

Del orden de \(n^{2}\): con \(2 \times 10^{4}\) elementos son unos \(2 \times 10^{8}\) sumas. Es correcto, pero lento.

¿Doscientos millones de sumas es mucho? En LeetCode, una solución en C++ tiene alrededor de un segundo, y eso alcanza para unos \(10^{8}\) pasos sencillos. Esta queda en el límite y con frecuencia excede el tiempo.

LC 560 · Por qué no dos punteros

La ventana del Taller 1 no sirve aquí

  • Una ventana deslizante crece por la derecha cuando falta suma y se encoge por la izquierda cuando sobra.
  • Eso supone que agregar un elemento hace crecer la suma. Con negativos no es cierto: en [1, 2, −2, 2, 1], agregar el −2 la hace bajar.
  • Con negativos, una ventana que ya se pasó de k todavía puede volver a sumar k si se alarga. Encogerla descartaría soluciones.

¿Y si primero ordeno el arreglo? Ordenar cambia qué elementos quedan juntos, y los subarreglos dependen de ese orden. Después de ordenar [1, 2, −2, 2, 1], el arreglo tiene otros subarreglos.

LC 560 · La idea

Sumas prefijas: un subarreglo es una resta

\(S_i\) es la suma de los primeros \(i\) elementos, con \(S_0 = 0\).

\(i\)012345
\(S_i\)013134
\[ \text{suma de } nums[j..i-1] = S_i - S_j \]

Por ejemplo, [2, 1] son los elementos 3 y 4: \(S_5 - S_3 = 4 - 1 = 3\).

LC 560 · Reformular

De "probar cada inicio" a "contar lo que ya vi"

  • Un subarreglo que termina donde vamos suma \(k\) cuando \(S_i - S_j = k\), es decir, cuando \(S_j = S_i - k\).
  • Para cada fin, la pregunta deja de ser "¿qué inicios funcionan?" y pasa a ser: ¿cuántas sumas prefijas anteriores valen \(S_i - k\)?
  • Esa pregunta la contesta en orden uno un mapa de suma prefija a cuántas veces apareció.

La clave del mapa no es un elemento de la entrada: es un estado del recorrido, la suma hasta ese momento.

LC 560 · Dos detalles

Lo que hace falta para que el conteo sea correcto

  • El mapa empieza con vistos[0] = 1. Es \(S_0\), el prefijo vacío. Sin él, los subarreglos que empiezan en la posición 0 no se cuentan: con nums = [3] y k = 3 el resultado saldría 0.
  • Primero se consulta y después se guarda. Si se guardara antes, con k = 0 cada suma se encontraría a sí misma y se contaría el subarreglo vacío.
  • Se cuentan veces, no solo presencia. Si \(S_i - k\) apareció dos veces, hay dos subarreglos distintos que terminan aquí. Por eso el mapa guarda un contador y no es un unordered_set.
LC 560 · Escribir el código

Una pasada, una consulta y una escritura por elemento

int subarraySum(vector<int>& nums, int k) {
unordered_map<int, int> vistos;
vistos[0] = 1;
int suma = 0;
int cuenta = 0;
int n = nums.size();
for (int i = 0; i < n; i++) {
suma = suma + nums[i];
int buscado = suma - k;
if (vistos.count(buscado) > 0)
cuenta = cuenta + vistos[buscado];
vistos[suma] = vistos[suma] + 1;
}
return cuenta;
}
El plan: recorrer una vez, llevando la suma prefija, y preguntarle al mapa por la suma que haría falta.
La firma de LeetCode. Regresa cuántos subarreglos suman k.
El mapa: de suma prefija a cuántas veces apareció. Un contador por clave.
El prefijo vacío. \(S_0 = 0\) apareció una vez antes de empezar.
Dos acumuladores: la suma prefija actual y el total de subarreglos encontrados.

¿Cabe suma en un int? Sí: a lo más \(2 \times 10^{4}\) elementos de valor absoluto hasta 1000 dan \(2 \times 10^{7}\).
El recorrido. Al sumar nums[i], suma pasa a ser \(S_{i+1}\): la suma de todo hasta este elemento.
La consulta. Se buscan las sumas anteriores que valen suma - k, y se suman todas sus apariciones. Se pregunta con count para no crear entradas vacías en el mapa.
Guardar después. La suma actual se registra hasta que terminó la consulta, para que ningún subarreglo termine antes de empezar.
Listo. Cada elemento hizo una consulta y una escritura.
LC 560 · Ejecución

Contar con sumas prefijas, elemento por elemento

LC 560 · Costo y pruebas

De \(n^{2}\) a \(n\)

  • Una pasada, con una consulta y una escritura al mapa por elemento: orden \(n\) en promedio. La memoria es orden \(n\), una entrada por suma distinta.
  • nums = [3], k = 3 → 1. Revisa el prefijo vacío.
  • nums = [0, 0, 0], k = 0 → 6. Revisa el orden de consultar y guardar, y que se cuenten veces.
  • nums = [1, −1, 1], k = 1 → 3. Revisa los negativos.
Checkpoint

Si se quita la línea vistos[0] = 1;, ¿qué regresa la función con nums = [1, 2] y k = 3?

B. Al llegar al 2, suma vale 3 y se busca 3 − 3 = 0. El subarreglo empieza en la posición 0, así que su suma es \(S_2 - S_0\), y sin la entrada del prefijo vacío el 0 no está en el mapa. No falla (C): count regresa 0 y la cuenta queda en 0.
