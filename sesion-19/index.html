8.3 El árbol splay

8.3 · Árboles splay

Un BST que se reorganiza al usarse

  • Es un BST sin información de balance en los nodos: no guarda alturas ni factores de balance.
  • Después de cada acceso (búsqueda, inserción, incluso una búsqueda fallida), el nodo alcanzado sube hasta la raíz con rotaciones. Esa operación se llama splay.
  • Los elementos que se usan seguido quedan cerca de la raíz, y acceder a ellos otra vez cuesta poco.
  • Leer también modifica el árbol: una búsqueda reescribe punteros.
8.3 · Rotaciones

rotarDer, línea por línea

8.3 · Rotaciones

Las dos rotaciones


Nodo* rotarDer(Nodo* y) {
    Nodo* x = y->izq;
    y->izq = x->der;
    x->der = y;
    return x;
}
Nodo* rotarIzq(Nodo* x) {
    Nodo* y = x->der;
    x->der = y->izq;
    y->izq = x;
    return y;
}

Cambian dos punteros y conservan el inorden: O(1). Son las rotaciones del AVL; el splay decide cuándo y en qué orden se aplican.

8.3 · La operación splay

Los tres casos, según dónde está el buscado

r es la raíz del subárbol que se procesa, p su hijo izquierdo, x el nodo que se busca.

CasoCuándoRotaciones
zigx es p: falta un solo niveluna: rotarDer(r)
zig-zigx está a la izquierda de pdos a la derecha: primero sobre r (el abuelo), luego sobre p
zig-zagx está a la derecha de protarIzq(p) y luego rotarDer(r), como el caso doble del AVL

Si x está a la derecha de r, los tres casos son el espejo.

splay(40): un zig-zag

splay(10): tres zig-zig seguidos

splay en código


Nodo* splay(Nodo* r, int k) {
    if (r == nullptr) return r;
    if (k < r->dato) return splayIzq(r, k);
    if (k > r->dato) return splayDer(r, k);
    return r;
}
Nodo* splayIzq(Nodo* r, int k) {
    Nodo* p = r->izq;
    if (p == nullptr) return r;
    if (k < p->dato) {
        p->izq = splay(p->izq, k);
        r = rotarDer(r);
    } else if (k > p->dato) {
        p->der = splay(p->der, k);
        if (p->der != nullptr)
            r->izq = rotarIzq(p);
    }
    if (r->izq == nullptr) return r;
    return rotarDer(r);
}
8.3 · La operación splay

Lo que hay que notar del código

  • La recursión baja de dos en dos niveles y las rotaciones ocurren al regresar, de abajo hacia arriba.
  • En el zig-zig se rota primero el abuelo (r = rotarDer(r)) y después el padre. Ese orden importa, como se ve en el siguiente slide.
  • Si k no está, sube el último nodo visitado: los dos return r cuando un hijo es nullptr.
  • splayDer es el espejo: izq ↔ der, < ↔ >, rotarDer ↔ rotarIzq. Lo escribes en la práctica.

Sleator y Tarjan agrupan los niveles desde abajo; esta versión, desde arriba. Con profundidad impar el zig sobrante queda abajo. La garantía amortizada es la misma.

En un splay, el 10 es hijo izquierdo del 20 y el 20 es hijo izquierdo del 30. Se accede al 10. ¿Cuál es la primera rotación?

y eliminar

8.3 · Operaciones

Buscar e insertar: el trabajo lo hace splay


bool contiene(Nodo*& raiz, int k) {
    raiz = splay(raiz, k);
    if (raiz == nullptr) return false;
    return raiz->dato == k;
}
Nodo* insertar(Nodo* raiz, int k) {
    raiz = insertarBST(raiz, k);
    return splay(raiz, k);
}
  • contiene recibe la raíz por referencia: buscar cambia la raíz del árbol.
  • insertarBST es la inserción normal de un BST. Después, splay sube al recién insertado.
8.3 · Operaciones

Eliminar: subir, quitar y unir


Nodo* eliminar(Nodo* raiz, int k) {
    raiz = splay(raiz, k);
    if (raiz == nullptr) return nullptr;
    if (raiz->dato != k) return raiz;
    Nodo* izq = raiz->izq;
    Nodo* der = raiz->der;
    delete raiz;
    if (izq == nullptr) return der;
    // k es mayor que todo izq: sube su máximo
    izq = splay(izq, k);
    izq->der = der;
    return izq;
}

Tras splay(izq, k), la raíz de izq es su máximo y no tiene hijo derecho: ahí se cuelga der.

Checkpoint

Se llama a contiene(raiz, 25) en un splay donde el 25 no está. ¿Qué nodo queda en la raíz?

C. Cuando un hijo es nullptr, splayIzq (o su espejo) devuelve r, y las llamadas de arriba lo siguen subiendo. Queda en la raíz el último nodo del camino, que siempre es el predecesor o el sucesor de 25 en el árbol. Una búsqueda fallida también reorganiza el árbol; por eso eliminar funciona aunque la clave no exista.

8.3 Complejidad amortizada

8.3 · Complejidad amortizada

Qué promete exactamente el splay

  • Un acceso individual puede costar O(n): el árbol puede estar degenerado en ese momento, como la cadena de hace unos slides.
  • Amortizado O(log n): cualquier secuencia de m operaciones cuesta O(m log n) en total. Un acceso caro deja el árbol más bajo, y los siguientes accesos cuestan menos.
  • Promedio supone una distribución de entradas; peor caso acota cada operación por separado; amortizado acota la secuencia completa sin suponer nada sobre las entradas.
  • El push_back de std::vector sigue el mismo patrón: O(1) amortizado, con redimensionamientos O(n) de vez en cuando.
8.3 · Patrón de acceso

La apuesta: accesos sesgados contra uniformes

8.3 · Patrón de acceso

Cuándo conviene un splay

  • Conviene cuando pocos elementos concentran la mayoría de los accesos, o cuando lo recién usado se vuelve a usar pronto.
  • No conviene si cada operación tiene un límite de tiempo: la garantía es sobre la secuencia, y un acceso suelto puede costar O(n).
  • Tampoco si varios hilos leen a la vez: cada lectura modifica el árbol, así que hasta las búsquedas necesitan exclusión mutua.
  • A favor: no guarda nada extra en los nodos y el código es más corto que el de un AVL.
Checkpoint

Un splay garantiza O(log n) amortizado por operación. ¿Qué afirmación es correcta?

A. La cota amortizada es sobre la secuencia completa y no supone nada sobre las entradas. La opción B describe una cota de peor caso por operación, que el splay no da: el acceso al fondo de una cadena cuesta O(n). La opción C describe un costo promedio, que depende de suponer una distribución de entradas.

Por qué importa hoy

La apuesta por la localidad temporal

  • El splay apuesta a que lo recién usado se volverá a usar. La misma hipótesis sostiene el prompt caching: los tokens de entrada cacheados cuestan hasta ~10× menos cuando la apuesta acierta (los de salida se pagan igual).
  • Las políticas LRU de la caché KV de un modelo hacen la misma apuesta al decidir qué desalojar.
  • Con un patrón de acceso uniforme, la ventaja desaparece y el splay pierde contra un AVL. Elegir la estructura es elegir qué apuesta sobre el patrón de acceso estás dispuesto a hacer.
STL

La STL no trae splay

  • No hay estructura auto-ajustable en la biblioteca estándar: std::map y std::set rebalancean por forma, ignorando el patrón de acceso.
  • Implementar una estructura propia se justifica cuando hay un patrón de acceso medido con datos que la estructura estándar desaprovecha.
  • Sin esa medición, la implementación propia agrega costo de mantenimiento y riesgo de errores a cambio de nada.
