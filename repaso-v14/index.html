R14 · Operadores aritméticos

a + b es una llamada a un método


class Fraccion {
    int num_, den_;
public:
    Fraccion(int n = 0, int d = 1) : num_(n), den_(d) {}

    Fraccion operator+(const Fraccion& o) const {
        return Fraccion(num_ * o.den_ + o.num_ * den_,
                        den_ * o.den_);
    }
};
// el compilador traduce  a + b  a  a.operator+(b)
  • El operando izquierdo es el objeto sobre el que se llama el método, así que dentro accedes a sus campos sin calificarlos. El derecho llega como parámetro.
  • Devuelve Fraccion por valor: la suma es un objeto nuevo que se construye dentro de la función. Devolver Fraccion& apuntaría a algo que deja de existir al retornar.
Checkpoint

¿Por qué operator+ devuelve Fraccion por valor y no Fraccion&?

B. La suma no existe antes de la llamada: se crea en el cuerpo de la función y se destruye al terminar, así que una referencia a ella apunta a memoria liberada. La opción A es falsa, y operator= y operator[] sí devuelven referencias, porque ahí el objeto referido sobrevive a la llamada. La C invierte el argumento: el costo de la copia no es lo que decide, el tiempo de vida sí.
R14 · Operadores de comparación

Comparar con == y definir el resto encima


bool operator==(const Fraccion& o) const {
    return num_ * o.den_ == o.num_ * den_;   // producto cruzado
}

bool operator!=(const Fraccion& o) const {
    return !(*this == o);                    // reusa el anterior
}
  • El parámetro es const Fraccion& para no copiar y el método es const porque comparar no modifica nada. Sin ese const no puedes comparar objetos constantes.
  • El producto cruzado hace que 1/2 == 2/4 sea cierto aunque los campos difieran. Comparar campo por campo daría falso.
  • !=, >, <= y >= se escriben en términos de == y <. Definir solo esos dos y derivar los demás evita que un día dejen de ser coherentes entre sí.
R14 · Acceso indexado

operator[] se escribe dos veces


class Arreglo {
    int* datos_;
public:
    int& operator[](int i) { return datos_[i]; }
    const int& operator[](int i) const { return datos_[i]; }
};

Arreglo a(3);
a[0] = 7;                    // usa la primera: int& es asignable
const Arreglo b = a;
std::cout << b[0];           // usa la segunda: b es const
  • Devolver int& es lo que permite que a[0] aparezca a la izquierda de un igual. Con int a secas devolverías una copia y la asignación no llegaría al arreglo.
  • La segunda versión existe para los objetos const, que solo pueden llamar métodos const. El compilador elige una u otra según el objeto.
  • [] no verifica el índice, igual que en std::vector. La versión que sí lanza excepción se llama at() y aparece en R18.
Checkpoint

Declaras únicamente int operator[](int i) const; y la línea a[0] = 7; no compila. ¿Qué falta?

C. a[0] devuelve una copia del elemento; asignarle un valor no tendría a dónde llegar, y el compilador lo rechaza. La opción B quita el const del método pero el retorno sigue siendo int por valor, así que el error persiste. La A confunde friend, que da acceso a lo privado desde fuera de la clase, con el tipo de retorno: un método ya tiene ese acceso.
R14 · Operador de salida

Como miembro, << queda al revés


class Fraccion {
    int num_ = 1, den_ = 2;
public:
    std::ostream& operator<<(std::ostream& os) const {
        return os << num_ << '/' << den_;
    }
};

Fraccion f;
f << std::cout;      // compila e imprime 1/2
std::cout << f;      // error: ostream no tiene ese operator<<
  • En un operador binario escrito como miembro, el operando izquierdo es siempre el objeto de la clase. Eso fija el orden en f << std::cout, que nadie escribe.
  • Para std::cout << f el método tendría que vivir dentro de std::ostream, y esa clase es de la biblioteca estándar.
R14 · Operador de salida

<< como función libre y amiga


class Fraccion {
    int num_, den_;
public:
    friend std::ostream& operator<<(std::ostream& os,
                                    const Fraccion& f);
};

std::ostream& operator<<(std::ostream& os, const Fraccion& f) {
    return os << f.num_ << '/' << f.den_;
}
  • Fuera de la clase el operador recibe dos parámetros y el flujo va primero, así que std::cout << f encaja.
  • Devuelve el mismo flujo por referencia: eso permite encadenar std::cout << f << '\n', donde el resultado de la primera llamada es el operando izquierdo de la segunda.
  • La declaración amiga le da acceso a num_ y den_. Si la clase ya expone num() y den() públicos, friend sobra.
Checkpoint

¿Qué se rompe si operator<< devuelve void en lugar de std::ostream&?

A. std::cout << f << '\n' se agrupa como (std::cout << f) << '\n': el resultado de la primera llamada es el operando izquierdo de la segunda. Con void ese operando no existe y el compilador falla. La opción B ignora ese encadenamiento, que es la única razón del tipo de retorno. La C describe un problema de orden de impresión que no ocurre: cada llamada escribe cuando se evalúa.
R14 · Miembro o función libre

Dónde va cada operador

OperadoresDóndeRazón
= [] () ->Miembro, obligatorioEl estándar solo los admite dentro de la clase
+ - * == <Cualquiera de las dosComo función libre, el operando izquierdo también admite conversión
<< >>Función libreEl operando izquierdo es el flujo, no tu objeto

Con operator+ como miembro, f + 2 compila porque el 2 se convierte a Fraccion con el constructor, pero 2 + f falla: el operando izquierdo debe ser ya un objeto de la clase. Como función libre funcionan los dos casos.

R14 · Criterio

Cuándo conviene sobrecargar

  • Cuando el operador significa sobre tu tipo lo mismo que sobre los tipos que ya conoce quien lee: + suma, == compara, << imprime.
  • Cuando conservas las expectativas asociadas: == no modifica los operandos, + produce un objeto nuevo, a + b vale lo mismo que b + a en un tipo numérico.
  • Si hace falta un comentario para explicar qué hace el operador, escribe un método con nombre. lista + x para agregar un elemento se lee peor que lista.agregar(x).
Sobrecarga cuando el significado del operador se entienda leyendo la expresión, sin abrir la definición de la clase.
R14 · Trampas comunes

El operator= incompleto


Arreglo& Arreglo::operator=(const Arreglo& o) {
    if (this == &o) return *this;     // 1. autoasignación
    delete[] datos_;
    datos_ = new int[o.n_];
    n_ = o.n_;
    for (int i = 0; i < n_; ++i) datos_[i] = o.datos_[i];
    return *this;                     // 2. referencia al objeto
}
  • Sin la línea 2, a = a; libera el arreglo y después copia desde memoria recién pedida. Los valores quedan basura y no hay ningún aviso.
  • Sin return *this; y con retorno void, la cadena c = b = a; deja de compilar.
  • El caso realista de autoasignación no es a = a escrito a mano, sino v[i] = v[j] dentro de un ciclo cuando i y j coinciden.
Checkpoint

Tu operator= libera y copia sin verificar this == &o. Ejecutas a = a;. ¿Qué ocurre?

B. Como o es el mismo objeto, el delete[] destruye justo lo que se va a copiar; la copia lee de un bloque nuevo sin inicializar. El programa no aborta, así que el error aparece más tarde y lejos. La opción A atribuye al compilador una comprobación que solo tú puedes hacer en tiempo de ejecución. La C describe el resultado deseado, que es exactamente lo que la verificación consigue.
R14 · Ejercicio

Completa la clase Fraccion

  1. Parte de una clase con num_, den_, un método privado reducir() y el constructor Fraccion(int n = 0, int d = 1) que lo llama.
  2. Agrega +, *, == y < como métodos, y << como función libre declarada amiga.
  3. Comprueba que Fraccion(1,2) + Fraccion(1,3) imprime 5/6 y que Fraccion(6,-8) imprime -3/4.

Fraccion Fraccion::operator+(const Fraccion& o) const {
    return Fraccion(num_ * o.den_ + o.num_ * den_,
                    den_ * o.den_);        // el ctor reduce
}
bool Fraccion::operator==(const Fraccion& o) const {
    return num_ * o.den_ == o.num_ * den_;
}
bool Fraccion::operator<(const Fraccion& o) const {
    return num_ * o.den_ < o.num_ * den_;  // den_ > 0 siempre
}
std::ostream& operator<<(std::ostream& os, const Fraccion& f) {
    return os << f.num_ << '/' << f.den_;
}

reducir() divide numerador y denominador entre std::gcd y deja el signo en el numerador. Con el denominador siempre positivo, < puede comparar productos cruzados sin invertir la desigualdad.
