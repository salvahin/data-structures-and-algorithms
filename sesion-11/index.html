6.1 Administración de memoria

6.1 · Administración de memoria

Dos regiones con reglas distintas

Stack

  • Variables locales; se libera sola al salir del scope.
  • Tamaño conocido en compilación.
  • Rápida: mover un puntero de tope.

Heap

  • Se pide con new; vive hasta que alguien la libere con delete.
  • Tamaño decidido en ejecución.
  • La responsabilidad de liberarla es del programador.

Toda estructura enlazada de este bloque vive en el heap: los nodos se crean y destruyen uno por uno, en tiempo de ejecución.

6.1 · Administración de memoria

new y delete: el par que debe cerrarse


int* p = new int(42);     // reserva un int en el heap
delete p;                 // lo libera; p queda apuntando a basura

int* arr = new int[n];    // reserva un arreglo de n ints
delete[] arr;             // forma correcta para arreglos

Nodo* nodo = new Nodo{7, nullptr};   // objeto con inicializador
delete nodo;              // llama al destructor y libera
  • Cada new tiene exactamente un delete; cada new[], un delete[].
  • Mezclar los pares (new[] con delete) es comportamiento indefinido.

6.1 · Administración de memoria

Los tres errores clásicos

  • Fuga — perder el último puntero a un bloque sin haberlo liberado. El bloque queda ocupado hasta que el proceso muere.
  • Puntero colgante — usar un puntero después de liberar el bloque al que apunta (use-after-free).
  • Doble liberación — hacer delete dos veces sobre el mismo bloque; corrompe las estructuras internas del asignador.

Ninguno de los tres falla de inmediato: son comportamiento indefinido. El programa puede correr bien hoy y fallar mañana con otros datos, otro compilador u otra carga.

Checkpoint

Después de ejecutar delete p;, ¿qué contiene p?

B. delete libera el bloque pero no toca la variable puntero: queda colgante. Ni el compilador ni el runtime detectan el uso posterior (opciones A y C describen lenguajes con recolector o verificación, no C++). Por eso conviene asignar p = nullptr; tras liberar cuando el puntero sobrevive.

6.2 Apuntadores y referencias

6.2 · Apuntadores y referencias

El puntero: una dirección con tipo


int x = 10;
int* p = &x;      // p guarda la direccion de x
*p = 20;          // desreferencia: modifica x a traves de p

int arr[4] = {3, 1, 4, 1};
int* q = arr;     // el nombre del arreglo decae a puntero

q + 1;            // avanza sizeof(int) bytes, no 1 byte
arr[i];           // equivale a *(arr + i)
  • La aritmética de punteros trabaja en unidades del tipo apuntado; el compilador multiplica por sizeof(T).
  • Un puntero puede valer nullptr, reasignarse, o apuntar a basura si no se inicializa.
6.2 · Apuntadores y referencias

Referencias y punteros a punteros


int x = 10;
int& r = x;       // alias: r ES x, no una copia
r = 20;           // modifica x; r no puede re-ligarse a otra variable

void pushFront(Nodo*& head, int v) {   // referencia a puntero
    head = new Nodo{v, head};          // el caller ve el cambio
}
// alternativa equivalente en C: Nodo** head
// y dentro: *head = new Nodo{v, *head};
  • Una referencia siempre está ligada a algo válido: sin nullptr, sin reasignación.
  • Para que una función modifique el puntero mismo (p. ej. head), recibe Nodo*& o Nodo**.

Checkpoint

Esta función no funciona: void pushFront(Nodo* head, int v) { head = new Nodo{v, head}; }. ¿Por qué?

C. Un puntero se copia como cualquier otro valor: la función modifica su copia y el head original queda igual (el nodo nuevo además se fuga). La firma correcta es Nodo*& head. La opción A liberaría un nodo que sigue en uso; la B es falsa — new siempre reserva en el heap.

7.1 Listas encadenadas

7.1 · Listas encadenadas

El modelo: nodos enlazados por punteros


struct Nodo {
    int   dato;
    Nodo* next;    // direccion del siguiente nodo, o nullptr
};

Nodo* head;        // la lista completa se alcanza desde aqui
// lista vacia: head == nullptr
  • Cada nodo vive en el heap, en una dirección arbitraria; el orden lógico lo dan los enlaces, no la posición en memoria.
  • Insertar y eliminar consiste en reasignar punteros; ningún elemento se desplaza.

7.1 · Listas encadenadas

Las mismas flechas, en código


// insertar x despues del nodo prev
Nodo* nuevo = new Nodo{x, prev->next};  // nuevo->next primero
prev->next  = nuevo;                    // re-enlazar despues

// eliminar el nodo que sigue a prev
Nodo* victima = prev->next;
prev->next    = victima->next;  // 1. puentear la victima
delete victima;                 // 2. liberar al final
  • La regla en ambos casos: no liberar ni sobrescribir un puntero mientras todavía se necesite leerlo.
  • Casos límite que el código de arriba no cubre: insertar antes de la cabeza y eliminar la cabeza. Ahí quien cambia es head — por eso la sesión pasada de punteros a punteros.
Checkpoint

Para eliminar el nodo que sigue a prev, un compañero escribe: delete prev->next; prev->next = prev->next->next;. ¿Qué está mal?

A. Tras el delete, prev->next es un puntero colgante y leerle ->next es comportamiento indefinido — puede "funcionar" en la máquina de pruebas y fallar en otra. El orden sí importa (descarta B); los nodos siguientes se conservan al puentear, no hay que liberarlos (descarta C).
Análisis · Lista vs. arreglo

Costo por operación

OperaciónArreglo / vectorLista encadenada

Insertar/eliminar dado el nodoO(n)O(1) — re-cablear

El O(1) de la lista tiene letra chica: aplica si ya tienes el puntero al nodo. Llegar hasta él cuesta O(n), y esa suma es la que se paga en la práctica.

Análisis · Lo que la O(·) no ve

La caché premia lo contiguo

  • Recorrer un vector: los elementos son vecinos en memoria; cada carga de caché trae varios de golpe y el prefetcher anticipa el siguiente.
  • Recorrer una lista: cada next puede saltar a cualquier parte del heap; en el peor caso, un fallo de caché por nodo — cientos de ciclos cada uno.
  • Resultado medible: en recorridos y búsquedas, un vector suele ganarle a una lista aun en operaciones donde la lista tiene mejor cota asintótica.

La notación asintótica es necesaria y no es suficiente: cuenta operaciones, no lo que cuesta cada acceso a memoria. La localidad decide el factor constante, y el factor a veces decide todo.

Checkpoint

Dos programas recorren 10 millones de enteros y los suman: uno sobre std::vector, otro sobre una lista encadenada. Ambos hacen O(n) operaciones, pero el del vector termina varias veces más rápido. ¿Por qué?

C. Las dos cotas son O(n); lo que cambia es el costo de cada acceso. El vector es contiguo y aprovecha caché y prefetcher; los nodos de la lista están dispersos y cada next puede costar un fallo de caché. La opción A confunde constante con cota; la B no es el factor dominante.

Por qué importa hoy

Por qué existe .contiguous() en PyTorch

  • Un tensor de PyTorch es una vista sobre un storage: un bloque contiguo de memoria, más strides que dicen cuántos elementos saltar por dimensión.
  • transpose no mueve datos: solo intercambia strides. La vista deja de ser contigua y el recorrido salta por la memoria — el mismo patrón de accesos de una lista encadenada.
  • .contiguous() copia los datos a un bloque nuevo en el orden de la vista. Cuesta una copia completa, y se paga porque los kernels sobre memoria contigua son mucho más rápidos.

La decisión de diseño es la de esta sesión: contigüidad contra flexibilidad, con la caché como juez.

STL

Punteros inteligentes: liberar sin acordarse


auto p = std::make_unique<Nodo>(7);   // dueño unico
// no hay delete: se libera solo al salir del scope,
// incluso si una excepcion interrumpe la funcion

auto q = std::make_shared<Nodo>(9);   // dueños multiples
// se libera cuando el ultimo shared_ptr muere (contador)
  • El patrón se llama RAII: el recurso se libera en el destructor del objeto que lo posee, y el compilador garantiza que ese destructor corre.
  • Regla moderna: new y delete explícitos casi no aparecen en código nuevo. Hoy los escribimos para entender qué hace el puntero inteligente por nosotros.
