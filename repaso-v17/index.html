R17 · Punto de partida

Esta función compila y da un resultado equivocado


#include <iostream>

int maximo(int a, int b) {
    return (a < b) ? b : a;
}

int main() {
    std::cout << maximo(3, 7)      << '\n';   // 7
    std::cout << maximo(2.5, 1.75) << '\n';   // 2
}

La segunda llamada convierte 2.5 y 1.75 a int antes de entrar. Adentro se comparan 2 y 1, y sale 2. Con -Wall -Wextra no aparece ninguna advertencia.

R17 · Plantillas de función

El tipo como parámetro


template <typename T>
T maximo(const T& a, const T& b) {
    return (a < b) ? b : a;
}

maximo(3, 7);          // T = int      -> 7
maximo(2.5, 1.75);     // T = double   -> 2.5
maximo(std::string("pera"), std::string("uva"));  // "uva"

La línea template <typename T> declara que T es un parámetro que se resuelve al compilar. El cuerpo es el mismo que ya tenías; solo se reemplazó int por T.

R17 · Deducción de tipos

Quién decide qué es T


maximo(3, 7);              // el compilador mira los argumentos:
                           // los dos son int, entonces T = int

maximo(3, 2.5);            // error: uno deduce int, otro double
                           // note: deduced conflicting types for 'T'

maximo<double>(3, 2.5);    // T escrito a mano: 3 se convierte
                           // a 3.0 y la llamada compila -> 3

La deducción no busca un tipo común ni promueve int a double. Compara los argumentos con los parámetros y exige que todos lleguen a la misma respuesta para T.

Checkpoint

Con template <typename T> T maximo(const T& a, const T& b);, ¿qué ocurre al escribir maximo(1, 2.0)?

C. Las conversiones implícitas de A y B ocurren cuando el tipo del parámetro ya está fijado, como en la función int maximo(int, int) del slide 3. En una plantilla el tipo todavía se está deduciendo, y dos deducciones contradictorias detienen la compilación. Se resuelve escribiendo el tipo: maximo<double>(1, 2.0).
R17 · Requisitos del tipo

La plantilla le pide operaciones a T


struct Persona { std::string nombre; int edad; };

Persona p1{"Ana", 20}, p2{"Beto", 22};
maximo(p1, p2);   // error: no match for 'operator<'
                  // (operand types are 'Persona' and 'Persona')
  • El cuerpo usa <, así que todo tipo que se pase debe tener operator<. Ese requisito no aparece escrito en la firma.
  • Cada plantilla pide solo lo que usa. Una que únicamente copie valores le exigirá a T ser copiable y nada más.
R17 · De clase concreta a plantilla

El punto de partida: CajaDeInt


class CajaDeInt {
public:
    explicit CajaDeInt(int v) : contenido_(v) {}
    int  ver() const  { return contenido_; }
    void poner(int v) { contenido_ = v; }
private:
    int contenido_;
};

Para guardar un std::string harías CajaDeString, con las mismas cuatro líneas y otro tipo. Ese es el trabajo que la plantilla elimina.

R17 · De clase concreta a plantilla

Caja<T>: la misma clase con un tipo abierto


template <typename T>
class Caja {
public:
    explicit Caja(const T& v) : contenido_(v) {}
    const T& ver() const   { return contenido_; }
    void poner(const T& v) { contenido_ = v; }
private:
    T contenido_;
};

Caja<int> c(7);
Caja<std::string> s("hola");

En una clase el tipo se escribe al usarla; no hay argumentos de los que deducirlo. Los parámetros pasan a const T& para no copiar tipos grandes.

R17 · Instanciación

Qué hace el compilador con la plantilla

Todo ocurre en compilación. Si nadie escribe Caja<double>, esa versión nunca existe en el ejecutable.

Checkpoint

En un programa que usa Caja<int> y Caja<std::string>, ¿cuántas clases genera el compilador?

A. Cada instanciación produce código propio, como si hubieras escrito CajaDeInt y CajaDeString a mano. B describe un modelo de genéricos con una sola clase compartida, como el de Java, donde el parámetro de tipo se borra al compilar y el tipo se maneja con conversiones. C confunde la plantilla con una clase: Caja<T> por sí sola no genera nada hasta que alguien la usa con un tipo.
R17 · Dónde vive la plantilla

Por qué la definición completa va en el header

  • Para generar Caja<int>, el compilador necesita el cuerpo de cada método, no solo su firma.
  • El compilador procesa una unidad de traducción a la vez (R0). Si main.cpp incluye una cabecera con solo las firmas, no tiene con qué generar el código.
  • Poner la definición en la cabecera hace que llegue a todo archivo que la incluya, justo donde se necesita.
Las plantillas se distribuyen como código fuente: cabecera con todo adentro, sin .cpp propio. Por eso los archivos de la STL son enormes.
R17 · Trampa común

Separar la plantilla en un .cpp


template <typename T>
class Caja {
public:
    void poner(const T& v);
private:
    T contenido_;
};
          

#include "caja.hpp"

template <typename T>
void Caja<T>::poner(const T& v) {
    contenido_ = v;
}
          

$ g++ -std=c++17 -Wall -Wextra main.cpp caja.cpp -o app
/usr/bin/ld: main.o: in function `main':
main.cpp:(.text+0x30): undefined reference to
                       `Caja<int>::poner(int const&)'
collect2: error: ld returned 1 exit status
Checkpoint

¿Por qué el enlazador no encuentra Caja<int>::poner si caja.cpp sí se compiló y sí se pasó al comando?

B. caja.o se generó correctamente y está vacío de poner: la plantilla solo produce código cuando alguien la instancia, y en ese archivo nadie lo hizo. main.o sí pidió Caja<int>::poner pero tampoco pudo generarlo, porque el header que incluyó solo traía la firma. La bandera de C no existe, y extern no aporta cuerpos.
R17 · Leer los errores

Cien líneas para un solo problema


$ g++ -std=c++17 orden.cpp 2>&1 | wc -l
114

$ g++ -std=c++17 orden.cpp 2>&1 | grep "error:"
predefined_ops.h:45:23: error: no match for 'operator<'
   (operand types are 'Persona' and 'Persona')
  • Las 110 líneas restantes son la cadena required from: por dónde llegó el compilador desde tu std::sort hasta el punto que falló.
  • La línea con required from here es la única que apunta a tu archivo. Ahí está la llamada que provocó todo.
R17 · Trampas comunes

Cuatro formas de perder media hora

  • Definir los métodos de la plantilla en un .cpp y leer undefined reference como si faltara un archivo en el comando.
  • Leer un error de plantilla de arriba hacia abajo. Conviene buscar primero error: y después required from here.
  • Olvidar <T> al definir un método fuera de la clase: void Caja::poner(...) no compila, va void Caja<T>::poner(...).
  • Suponer que Caja<int> y Caja<double> son tipos relacionados. Son dos clases sin parentesco: no se asignan entre sí.
R17 · Ejercicio

Convierte en plantilla la clase Arreglo de R13

  1. Toma la versión con regla de tres y cambia int por T en el campo, el new[], el operator[] y el constructor de copia.
  2. Deja todo dentro de arreglo.hpp, sin archivo de implementación.
  3. Pruébala con Arreglo<double> y con Arreglo<std::string>, copiando un objeto para verificar la copia profunda.

template <typename T>
class Arreglo {
public:
    explicit Arreglo(std::size_t n) : n_(n), datos_(new T[n]()) {}
    Arreglo(const Arreglo& o) : n_(o.n_), datos_(new T[o.n_]) {
        for (std::size_t i = 0; i < n_; ++i) datos_[i] = o.datos_[i];
    }
    ~Arreglo() { delete[] datos_; }
    T& operator[](std::size_t i) { return datos_[i]; }
    std::size_t tam() const { return n_; }
private:
    std::size_t n_;
    T* datos_;                 // antes: int* datos_;
};

El operator= de la regla de tres cambia igual: new T[n_] en vez de new int[n_]. Con new T[n]() los elementos quedan inicializados a cero para tipos numéricos y por su constructor por omisión para clases.
