G2 · Punto de partida

Quieres probar una idea que puede romper todo

Llevas once sesiones, tu clase compila y ahora quieres reescribirla de otra forma. La única maniobra que conoces es duplicar la carpeta antes de tocar nada.


cp -r r13-memoria arreglo_backup
  • Quedan dos copias del mismo código y nada registra en qué se diferencian: para saberlo hay que abrir los archivos y compararlos a ojo.
  • Si la idea funciona, los cambios se regresan a mano, archivo por archivo.
  • La copia no entra en la historia. En dos semanas, el nombre arreglo_backup no dice qué contenía ni por qué se creó.

G2 · Leer la historia

Qué cambió entre dos commits


$ git diff --stat HEAD~3 HEAD
 r09-tema/main.cpp | 1 +
 r10-tema/main.cpp | 1 +
 r11-tema/main.cpp | 1 +
 3 files changed, 3 insertions(+)

HEAD~3 significa tres commits antes del actual. Sin --stat, el mismo comando imprime las líneas exactas que entraron y salieron.


$ git diff
diff --git a/r00-compilacion/main.cpp b/r00-compilacion/main.cpp
index 2481a48..0e9df85 100644
--- a/r00-compilacion/main.cpp
+++ b/r00-compilacion/main.cpp
@@ -1,2 +1,2 @@
 #include <iostream>
-int main(){ std::cout << "hola\n"; }
+int main(){ std::cot << "hola\n"; }

Cuando algo deja de compilar, la pregunta útil no se contesta releyendo el archivo entero: se contesta comparando con el último commit que sí compilaba. Es el punto de partida de R12.

Checkpoint

Tu clase compilaba en el commit ed4156c de R10 y hoy, varios commits después, ya no compila. ¿Qué comando te dice qué líneas cambiaron desde entonces?

B. git diff acepta dos referencias cualesquiera y devuelve las líneas que las separan. A solo devuelve mensajes y hashes, que te sirven para elegir el commit pero no dicen qué se modificó. C mira un solo commit y, con --stat, solo cuenta archivos y líneas de ese commit, no la diferencia acumulada desde R10.
G2 · Ramas

Una rama es un nombre que apunta a un commit

Una rama guarda un hash de 40 caracteres, no archivos. HEAD indica en cuál de esos nombres estás parado: al hacer un commit, git escribe el commit nuevo y mueve ese nombre hacia adelante, mientras los demás se quedan donde estaban. Crear la rama prueba escribió un archivo de 41 bytes y no copió una sola línea del proyecto.

G2 · Ramas

Cambiar de rama cambia los archivos del disco


$ git switch -c sin-regla-de-tres
Switched to a new branch 'sin-regla-de-tres'

# creas r13-memoria/, la compilas y haces commit

$ git switch main
Switched to branch 'main'

$ git branch
* main
  sin-regla-de-tres
  • Al volver a main, la carpeta r13-memoria ya no está en el disco. Con git switch sin-regla-de-tres reaparece completa. Los archivos viven dentro del repositorio y git reescribe tu carpeta de trabajo en cada cambio de rama.
  • git branch lista los nombres y marca con * aquel al que apunta HEAD.
  • Lo que no está comiteado no está guardado: git intenta arrastrarlo a la otra rama y, si estorba, se niega a cambiar. Comitea antes de moverte.
Checkpoint

Estás en main con todo comiteado y ejecutas git switch -c prueba. ¿Qué ocurrió en ese instante?

C. La rama nueva nace apuntando al commit donde estabas, así que los dos nombres señalan lo mismo y el disco no cambia. A supone una copia de archivos que git no hace. B invierte el mecanismo: main sigue disponible y basta git switch main para recuperar su versión de los archivos, con o sin fusión.
G2 · Ramas

Ver las dos ramas a la vez


$ git log --oneline --graph --all
* 9c559d7 R13: Arreglo con regla de tres
| * 408de56 R13: Arreglo sin regla de tres
|/
* 650683f R11: ejercicio de la sesion
* ed4156c R10: ejercicio de la sesion
  • Cada * es un commit. La columna en la que aparece indica a qué línea de trabajo pertenece.
  • La barra |/ marca el punto donde las dos ramas se separaron: 650683f, el commit de R11, es el ancestro común.
  • Sin --all, git solo dibuja la historia alcanzable desde la rama actual y la otra rama no aparece.
G2 · Comparar

Las dos versiones de la misma clase


$ git diff sin-regla-de-tres con-regla-de-tres
diff --git a/r13-memoria/arreglo.h b/r13-memoria/arreglo.h
index ad22530..5e91cce 100644
--- a/r13-memoria/arreglo.h
+++ b/r13-memoria/arreglo.h
@@ -1,6 +1,8 @@
 class Arreglo {
 public:
     Arreglo(int n) : n_(n), datos_(new int[n]) {}
+    Arreglo(const Arreglo& o);
+    Arreglo& operator=(const Arreglo& o);
     ~Arreglo() { delete[] datos_; }
 private:
     int  n_;

El orden de los argumentos importa: git diff A B describe cómo pasar de A a B, así que las líneas con + están en B y faltan en A. Aquí la diferencia entre las dos ramas son las dos declaraciones que R13 llama regla de tres.

G2 · Fusionar

Fusionar cuando main no avanzó


$ git switch main
Switched to branch 'main'

$ git merge con-regla-de-tres
Updating 650683f..9c559d7
Fast-forward
 r13-memoria/arreglo.h | 10 ++++++++++
 1 file changed, 10 insertions(+)
 create mode 100644 r13-memoria/arreglo.h
  • Desde que nació la rama, main no recibió commits propios, así que su historia está contenida en la de la otra rama.
  • Git no combina nada: mueve el nombre main hasta 9c559d7. Eso es un fast-forward, y por eso no aparece ningún commit de fusión en el git log.
Checkpoint

git merge imprime Fast-forward y ninguna otra cosa. ¿Qué hizo git?

A. El fast-forward solo es posible cuando la rama de destino no tiene commits propios: su commit es ancestro del otro, así que adelantar el nombre basta. B describe la fusión real, que git usa cuando las dos ramas avanzaron por separado y que sí produce un commit extra. C invierte el orden de las cosas: git opera sobre commits y la carpeta de trabajo se reescribe como consecuencia.
G2 · Conflictos

Dos ramas cambiaron la misma línea


$ git merge prueba-a
Auto-merging r13-memoria/demo.cpp
CONFLICT (content): Merge conflict in r13-memoria/demo.cpp
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU r13-memoria/demo.cpp
      

#include <iostream>
int main() {
<<<<<<< HEAD
    std::cout << "version con delete\n";
=======
    std::cout << "version con delete[]\n";
>>>>>>> prueba-a
}

UU marca el archivo como no fusionado. Git combinó todo lo que pudo y se detuvo en las líneas que no supo decidir.

G2 · Conflictos

Resolver es editar el archivo y cerrar el merge

  • <<<<<<< HEAD abre el bloque. Lo que sigue es la versión de la rama donde estabas parado.
  • ======= separa las dos versiones; debajo va la de la rama que estás fusionando, y >>>>>>> prueba-a cierra el bloque con su nombre.
  • Abre el archivo, deja el código que quieres —una versión, la otra o una mezcla— y borra las tres marcas. Después, el conflicto se cierra igual que cualquier cambio.

$ git add r13-memoria/demo.cpp
$ git commit -m "Merge: me quedo con delete[]"
$ git log --oneline --graph
*   765eee1 Merge: me quedo con delete[]
|\
| * 5fc24b8 R13: prueba con delete[]
* | 28a9d25 R13: prueba con delete
|/
* edcf2df R13: demo base

Si el conflicto se complica, git merge --abort cancela la fusión y deja el proyecto como estaba antes de empezarla.

G2 · Volver atrás

Deshacer un commit que ya subiste


$ git revert --no-edit 650683f
[main 4f155c6] Revert "R11: ejercicio de la sesion"
 Date: Thu Aug 20 16:29:21 2026 -0600
 1 file changed, 1 deletion(-)
 delete mode 100644 r11-tema/main.cpp
  • Git calcula el cambio inverso del commit señalado y lo graba como un commit nuevo, 4f155c6. El original sigue en git log, con su fecha y su mensaje.
  • git reset --hard hace algo distinto: mueve el nombre de la rama hacia atrás y descarta los commits posteriores en tu copia.
  • Sobre historia ya publicada eso obliga a git push --force, que reemplaza en el servidor commits que otros ya descargaron. Quien tenga esa rama se queda con una historia que ya no existe.
Checkpoint

Subiste a GitHub un commit que rompe la compilación y un compañero ya lo descargó. ¿Qué haces?

B. El revert deja el proyecto sin el cambio dañino y conserva el registro de que ocurrió: el commit original permanece en el historial, acompañado del que lo invierte. A reescribe historia que ya está en la copia de tu compañero, y su repositorio quedará apuntando a commits que el servidor ya no tiene. C atribuye a git merge un criterio que no tiene: combina cambios y, cuando chocan, se detiene y te pregunta.
G2 · Trampas comunes

Cuatro formas de perder media hora


$ git checkout 6827b8f
Note: switching to '6827b8f'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

$ git switch -
Previous HEAD position was 6827b8f R13: demo base
Switched to branch 'main'
  • Visitar un commit por su hash deja HEAD sin rama. Los commits que hagas ahí no tienen nombre que los alcance. git switch - regresa a donde estabas.
  • Borrar una rama sin fusionar: error: The branch 'sin-regla-de-tres' is not fully merged. La -d minúscula es la protección; -D la ignora.
  • Comitear el archivo con las marcas adentro. El compilador falla en la línea de <<<<<<< HEAD, que no es C++, y el mensaje no menciona git por ningún lado.
  • Creer que borrar una rama borra sus commits. Si ya la fusionaste, sus commits viven en la historia de main; se va el nombre, no el trabajo.
G2 · Ejercicio

Dos ramas para la clase Arreglo

  1. Desde main, crea la rama sin-regla-de-tres con r13-memoria/arreglo.h: solo constructor y destructor. Comitea.
  2. Vuelve a main y crea con-regla-de-tres con la misma clase más el constructor de copia y el operator=. Comitea.
  3. Compara las dos ramas con git diff, fusiona la buena en main y borra la otra.

git switch -c sin-regla-de-tres
# arreglo.h: Arreglo(int n) y ~Arreglo()
git add r13-memoria/arreglo.h
git commit -m "R13: Arreglo sin regla de tres"
git switch main

git switch -c con-regla-de-tres
# la misma clase + constructor de copia y operator=
git add r13-memoria/arreglo.h
git commit -m "R13: Arreglo con regla de tres"
git diff sin-regla-de-tres con-regla-de-tres
git switch main
git merge con-regla-de-tres        # Fast-forward
git branch -d sin-regla-de-tres    # responde: not fully merged

El diff que verás es el del slide 11. La última línea falla a propósito: esa rama nunca se fusionó, así que git pide -D para borrarla. La versión que queda en main es el punto de partida de R13.
