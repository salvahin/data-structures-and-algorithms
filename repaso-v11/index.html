R11 · Punto de partida

Dos archivos, una función, un error de enlazado


#pragma once
int doble(int n) { return 2 * n; }
          

#include "util.h"
int usarA() { return doble(2); }
          

#include <iostream>
#include "util.h"
int usarA();
int main() {
    std::cout << usarA() + doble(1) << '\n';
}
          

$ g++ -std=c++17 -Wall -Wextra main.cpp a.cpp -o app
/usr/bin/ld: a.o: in function `doble(int)':
a.cpp:(.text+0x0): multiple definition of `doble(int)';
main.o:main.cpp:(.text+0x0): first defined here

El #pragma once está puesto y aun así hay dos definiciones. Antes de terminar esta sesión vas a saber por qué.

R11 · El reparto

El header promete, el .cpp cumple

En el .hEn el .cpp
La definición de la clase con sus miembrosEl cuerpo de cada método
Las declaraciones de los métodos (firma y punto y coma)Las funciones auxiliares que nadie más usa
Constantes y enum que otros archivos necesitanLas variables globales del módulo
Los #include que el header mismo necesitaLos #include que solo usa la implementación

El criterio operativo: en el header va lo que otro archivo necesita conocer para compilar; todo lo demás va en el .cpp. Cada línea que agregas al header la pagan todos los archivos que lo incluyen.

R11 · El reparto

La clase Punto en dos archivos


#ifndef PUNTO_H
#define PUNTO_H

class Punto {
    double x, y;
public:
    Punto();
    Punto(double a, double b);
    double distanciaAlOrigen() const;
    void imprimir() const;
};

#endif
          

#include "punto.h"
#include <iostream>
#include <cmath>

Punto::Punto() : x(0), y(0) {}
Punto::Punto(double a, double b)
    : x(a), y(b) {}

double Punto::distanciaAlOrigen() const {
    return std::sqrt(x * x + y * y);
}

<iostream> y <cmath> se quedan en el .cpp porque el header no los necesita para describir la clase.

R11 · El reparto

Qué se repite y qué no en la implementación


double Punto::distanciaAlOrigen() const {
    return std::sqrt(x * x + y * y);
}
  • Punto:: indica a qué clase pertenece el método; sin ese prefijo sería una función libre y el enlazador no la relacionaría con la declaración del header.
  • El const del final es parte de la firma y debe aparecer en los dos archivos. Si lo escribes solo en uno, el compilador ve dos métodos distintos.
  • Los valores por omisión de los parámetros se escriben únicamente en el header. Repetirlos en el .cpp es un error.
  • La lista de inicialización va en el .cpp, junto al cuerpo, no en la declaración.
Checkpoint

Declaras void imprimir() const; en punto.h y escribes void Punto::imprimir() { … } en punto.cpp. ¿Qué ocurre?

C. El const final forma parte de la firma, así que estás definiendo un método que la clase no declara, y eso el compilador lo detecta con la sola información del header: error: no declaration matches 'void Punto::imprimir()', seguido de note: candidate is: void Punto::imprimir() const. A trata el const como un comentario. B es el desenlace de otro caso: cuando la firma coincide pero nadie escribió el cuerpo en ningún archivo.
R11 · Qué hace realmente #include

El preprocesador pega texto

En R0 viste que g++ -E muestra el archivo con los #include ya resueltos. #include "punto.h" copia el contenido completo del header en ese punto exacto del archivo.


g++ -E main.cpp | grep -c ""      # cuenta las lineas resultantes
g++ -E main.cpp | grep "class Punto"

El resultado de pegar todos los headers en un .cpp es una unidad de traducción: lo que el compilador procesa de una sola vez para producir un archivo objeto. Cada .cpp genera una unidad de traducción independiente y no sabe nada de las demás.

R11 · Guardas de inclusión

Sin guarda, el texto se pega dos veces


#include "punto.h"     // pega la clase Punto
#include "figura.h"    // figura.h tambien incluye punto.h
      

In file included from figura.h:1, from main.cpp:2:
punto.h:1:7: error: redefinition of 'class Punto'
In file included from main.cpp:1:
punto.h:1:7: note: previous definition of 'class Punto'

La guarda de inclusión define un símbolo la primera vez y salta el contenido las siguientes. #pragma once hace lo mismo con una línea; no es estándar, pero g++, clang y MSVC lo aceptan.


#ifndef PUNTO_H
#define PUNTO_H
// contenido
#endif
        

#pragma once
// contenido
Checkpoint

¿Contra qué protege una guarda de inclusión?

B. La guarda actúa en el preprocesador y su alcance es un solo archivo en proceso de traducción. A describe justo lo que debe ocurrir: incluir el mismo header desde varios .cpp es normal y necesario, y la guarda no lo impide. C confunde etapas: el enlazador no ve clases, ve símbolos, y las definiciones de clase no generan símbolos.
R11 · Compilar y enlazar

Un objeto por cada .cpp, un enlazado al final


# compilar cada unidad de traduccion por separado
g++ -std=c++17 -Wall -Wextra -g -c main.cpp     # -> main.o
g++ -std=c++17 -Wall -Wextra -g -c punto.cpp    # -> punto.o

# enlazar los objetos en un ejecutable
g++ main.o punto.o -o programa
  • La bandera -c detiene el proceso antes del enlazado y deja un archivo objeto con el código máquina de esa unidad y una tabla de símbolos.
  • Al enlazar no hacen falta las banderas de lenguaje ni de advertencias: esa etapa no vuelve a leer el código fuente.
  • Si cambias punto.cpp, solo hay que rehacer punto.o y volver a enlazar. En un proyecto de treinta archivos la diferencia es de minutos.
R11 · Makefile

Las mismas órdenes, escritas una vez


CXX      = g++
CXXFLAGS = -std=c++17 -Wall -Wextra -g
OBJ      = main.o punto.o

programa: $(OBJ)
	$(CXX) $(OBJ) -o programa

main.o: main.cpp punto.h
	$(CXX) $(CXXFLAGS) -c main.cpp

punto.o: punto.cpp punto.h
	$(CXX) $(CXXFLAGS) -c punto.cpp

clean:
	rm -f $(OBJ) programa

Cada regla tiene la forma objetivo: dependencias y debajo, indentada con un carácter de tabulación real, la orden que produce el objetivo. Un espacio en lugar del tabulador da el error missing separator.

El Makefile se versiona: es código fuente. Los .o y el ejecutable que produce, no, y por eso están en el .gitignore que pusiste en G1. La regla clean borra exactamente lo mismo que git ignora.

R11 · Makefile

Cómo decide make qué recompilar

make compara la fecha de modificación del objetivo con la de sus dependencias. Si el objetivo es más nuevo que todas ellas, no hace nada.


$ make
g++ -std=c++17 -Wall -Wextra -g -c main.cpp
g++ -std=c++17 -Wall -Wextra -g -c punto.cpp
g++ main.o punto.o -o programa

$ touch punto.cpp   &&  make
g++ -std=c++17 -Wall -Wextra -g -c punto.cpp
g++ main.o punto.o -o programa

$ touch punto.h     &&  make
g++ -std=c++17 -Wall -Wextra -g -c main.cpp
g++ -std=c++17 -Wall -Wextra -g -c punto.cpp
g++ main.o punto.o -o programa

Tocar el header rehace los dos objetos porque los dos lo declaran como dependencia. Omitir punto.h de esas reglas es la causa habitual de ejecutar un binario que no refleja los cambios.

Checkpoint

Agregas un método a punto.h, escribes su cuerpo en punto.cpp y corres make. El Makefile declara main.o: main.cpp sin mencionar el header. ¿Qué pasa?

C. make no lee el código fuente ni sigue los #include: solo compara fechas de los archivos que tú listaste. Con main.cpp sin cambios, main.o se conserva tal cual, compilado contra la clase vieja. A atribuye a make un análisis que no hace. B describe otro problema, el de las definiciones en el header.
R11 · La trampa del arranque

Definir una función en el header la duplica

  • #pragma once evita que util.h se pegue dos veces en la misma unidad de traducción. No puede hacer nada entre unidades distintas.
  • main.cpp y a.cpp se compilan por separado, y cada uno recibe su copia del cuerpo de doble. Al enlazar hay dos símbolos con el mismo nombre.
  • La regla que el enlazador aplica es que cada función debe tener exactamente una definición en todo el programa.

#pragma once
int doble(int n);                       // declaracion: correcto
inline int triple(int n) { return 3 * n; }  // inline: tambien

La palabra inline autoriza copias idénticas en varias unidades y le pide al enlazador que se quede con una. Los métodos escritos dentro del cuerpo de la clase ya son inline de forma implícita, y por eso punto.h no da problemas.

R11 · Trampas comunes

Cuatro fallas que produce la separación

  • Definir funciones libres en el header e incluirlo desde dos .cpp: multiple definition al enlazar.
  • Olvidar el #endif de la guarda, o repetir el mismo símbolo de guarda en dos headers distintos, lo que hace desaparecer el segundo en silencio.
  • Escribir using namespace std; en un header: se lo impone a todos los archivos que lo incluyan, sin que ellos puedan evitarlo.
  • Compilar solo el .cpp que cambiaste y olvidar pasar el resto de los objetos al enlazar: undefined reference.
R11 · Ejercicio

Divide un programa monolítico en tres archivos

  1. Toma la clase Punto de R10, con sus constructores, su destructor y sus métodos, escrita entera dentro de main.cpp.
  2. Sepárala en punto.h, punto.cpp y main.cpp, con guarda de inclusión.
  3. Escribe el Makefile con las reglas del objetivo, de cada objeto y de clean, y comprueba con touch que solo se recompila lo necesario.

$ ls
Makefile  main.cpp  punto.cpp  punto.h

$ make
g++ -std=c++17 -Wall -Wextra -g -c main.cpp
g++ -std=c++17 -Wall -Wextra -g -c punto.cpp
g++ main.o punto.o -o programa

$ ./programa
(3, 4)
5

$ make            # nada cambio: make no hace nada
make: 'programa' is up to date.

El reparto queda así: en punto.h la clase con las firmas y el punto y coma; en punto.cpp los cuerpos con el prefijo Punto:: y los #include de <iostream> y <cmath>; en main.cpp solo #include "punto.h" y el uso de la clase.
