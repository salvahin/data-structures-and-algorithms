R16 · Punto de partida

El mismo objeto, dos áreas distintas


class Figura {
public:
    double area() const { return 0.0; }
};
class Circulo : public Figura {
    double r_;
public:
    Circulo(double r) : r_(r) {}
    double area() const { return 3.14159 * r_ * r_; }
};
      

Circulo c(2.0);
Figura* f = &c;             // f apunta al mismo objeto
std::cout << c.area();      // 12.5664
std::cout << f->area();     // 0
R16 · Enlace dinámico

virtual aplaza la decisión hasta la ejecución


class Figura {
public:
    virtual double area() const { return 0.0; }
    virtual ~Figura() = default;
};
class Circulo : public Figura {
    double r_;
public:
    double area() const override { return 3.14159 * r_ * r_; }
};                             // ahora f->area() devuelve 12.5664
  • Sin virtual, el compilador elige el método con el tipo de la expresión: f es Figura*, así que llama a Figura::area.
  • Con virtual, la elección la hace el programa en ejecución consultando el objeto al que se llegó. Eso es el enlace dinámico.
R16 · Enlace dinámico

Cómo llega la llamada al método correcto

Cada clase con métodos virtuales tiene una vtable, y cada objeto guarda un puntero a la de su clase. El costo por llamada es ese salto adicional.

Checkpoint

Con area() sin virtual, Figura* f = &c; y f->area() devuelve 0 aunque c es un Circulo. ¿Por qué?

B. El compilador ve una expresión de tipo Figura* y escribe una llamada fija a Figura::area. La opción A describe el slicing, que aquí no ocurre: f apunta al Circulo entero y c.area() sobre ese mismo objeto sí devuelve 12.5664. La C invierte la relación: override solo verifica que la firma coincida con un método virtual de la base, y sin virtual escribirlo es un error de compilación.
R16 · Punteros y referencias

El enlace dinámico viaja por puntero o referencia


void porValor(Figura f)        { std::cout << f.area(); }
void porRef(const Figura& f)   { std::cout << f.area(); }
void porPtr(const Figura* f)   { std::cout << f->area(); }

Circulo c(2.0);
porValor(c);      // 0
porRef(c);        // 12.5664
  • Una variable de tipo Figura ocupa exactamente lo que ocupa una Figura. Copiar un Circulo ahí deja fuera el radio, y con él la vtable del círculo.
  • Una referencia o un puntero guardan dónde vive el objeto. El objeto no cambia de tipo, así que su vtable sigue siendo la que era. Es la razón de que R8 vaya antes que esta sesión.
R16 · override

override convierte un error silencioso en uno de compilación


// en la base
virtual double area() const;

// en la derivada, sin override: compila y no sobreescribe nada
double area();                 // le falta const

// con override, el compilador lo revisa
double area() override;        // error claro, en la línea exacta
      

error: 'double D::area()' marked 'override',
       but does not override

Escribe override en cada redefinición. Es la única forma barata de enterarte de que una firma dejó de coincidir.

R16 · Sobrecarga y sobreescritura

Dos mecanismos con nombres parecidos

Sobrecarga (R5, R14)Sobreescritura (R16)
Qué esVarias funciones con el mismo nombre en un mismo ámbitoUn método virtual de la base redefinido en la derivada
FirmasTienen que ser distintasTienen que ser idénticas, const incluido
Quién eligeEl compilador, por los tipos de los argumentosEl programa en ejecución, por el objeto real
RequiereNada másvirtual en la base y puntero o referencia

Cambiar un parámetro convierte una sobreescritura en una sobrecarga, y el programa sigue compilando.

Checkpoint

La base declara virtual void dibujar(int) const; y la derivada void dibujar(int);. ¿Qué relación hay entre las dos?

C. Falta el const final, así que las firmas difieren y no hay sobreescritura; una llamada por Base* sigue ejecutando la versión de la base. La opción A cuenta solo los parámetros y olvida que const forma parte de la firma de un método. La B espera un diagnóstico que no llega: el compilador acepta el código, y ese silencio es justo el motivo de escribir override.
R16 · Sobrecarga y sobreescritura

El caso que confunde, ejecutado


class Base {
public:
    virtual void f(int x) { std::cout << "Base::f(int)\n"; }
};
class Derivada : public Base {
public:
    void f(double x) { std::cout << "Derivada::f(double)\n"; }
};
Derivada d;
d.f(3);            // Derivada::f(double)
Base* p = &d;
p->f(3);           // Base::f(int)

d.f(3) busca el nombre f en Derivada, lo encuentra y deja de mirar la base, así que convierte el 3 a double. p->f(3) parte de Base, donde f(int) es virtual, y no hay ninguna versión que la sobreescriba.

R16 · Clases abstractas

= 0 obliga a la derivada a responder


class Figura {                                  // clase abstracta
public:
    virtual double area() const = 0;            // virtual pura
    virtual std::string nombre() const = 0;
    virtual ~Figura() = default;
};
class Rectangulo : public Figura {
    double a_, b_;
public:
    Rectangulo(double a, double b) : a_(a), b_(b) {}
    double area() const override { return a_ * b_; }
    std::string nombre() const override { return "Rectangulo"; }
};

Una clase abstracta no se puede instanciar: Figura f; da cannot declare variable to be of abstract type. Una derivada que deje sin definir alguna función pura sigue siendo abstracta y tampoco se instancia.

R16 · Clases abstractas

La base declara el contrato y nadie más lo repite


double areaTotal(const std::vector<Figura*>& figs) {
    double total = 0.0;
    for (const Figura* f : figs) total += f->area();   // no sabe cuál es
    return total;
}
  • areaTotal se escribió una vez y sirve para cualquier figura, presente o futura.
  • Agregar un Triangulo solo pide una clase que derive de Figura y defina las dos funciones puras.
  • El contenedor guarda Figura*: un vector por valor rebanaría cada figura al insertarla.
Checkpoint

Con Figura declarando virtual double area() const = 0;, ¿cuál de estas líneas no compila?

A. Crear un objeto exige saber qué hace cada método, y area() no tiene cuerpo en Figura; el compilador responde cannot declare variable to be of abstract type. Las opciones B y C no crean ninguna Figura: declaran un puntero y una referencia que apuntarán a un objeto derivado, que es la única manera de usar una clase abstracta.
R16 · Destructor virtual

Qué destructor no se ejecuta


class Base {
public:
    ~Base() { std::cout << "~Base()\n"; }      // sin virtual
};
class Derivada : public Base {
    int* buffer_;
public:
    Derivada() : buffer_(new int[1000]) { }
    ~Derivada() { delete[] buffer_; std::cout << "~Derivada()\n"; }
};
Base* p = new Derivada();   delete p;
      

sin virtual:   ~Base()
con virtual:   ~Derivada()   ~Base()

Sin virtual, delete p llama solo a ~Base y buffer_ se fuga.

R16 · Trampas comunes

Tres formas de perder el polimorfismo


Circulo c(2.0);            // Figura: base concreta, area() virtual
Figura  g = c;             // slicing: g.area() da 0
Figura& r = c;             // r.area() da 12.5664

std::vector<Figura>  v1;   // rebana cada figura al insertarla
std::vector<Figura*> v2;   // conserva el objeto completo
  • Asignar un derivado a una variable del tipo base copia solo el subobjeto base, y el compilador lo acepta en silencio.
  • Con la Figura abstracta del slide 12, la línea 2 no compila y v1.push_back(c) tampoco.
  • Las otras dos: destructor de la base sin virtual, y redefinir con una firma distinta creyendo que hubo sobreescritura.
Checkpoint

Con ~Base sin virtual, ejecutas Base* p = new Derivada(); delete p; y ambos destructores imprimen su nombre. ¿Qué sale?

C. delete p a través de un puntero a base con destructor no virtual es comportamiento indefinido; en la práctica el compilador lo resuelve con el tipo del puntero, así que solo corre ~Base() y todo lo que ~Derivada() iba a liberar se queda reservado. La opción A es lo que ocurre al marcar virtual ~Base(), y también el orden correcto. La B invierte la jerarquía: el destructor de la base se ejecuta siempre, porque el subobjeto base existe en todos los casos.
R16 · Ejercicio

Figuras con área polimórfica

  1. Declara Figura abstracta con area() y nombre() puras y destructor virtual.
  2. Deriva Circulo y Rectangulo y define las dos funciones con override.
  3. Llena un std::vector<Figura*>, recórrelo imprimiendo nombre y área, acumula el total y libera cada elemento. Compila con -fsanitize=address y verifica que no reporta fugas.

std::vector<Figura*> figs;
figs.push_back(new Circulo(1.0));
figs.push_back(new Rectangulo(3.0, 4.0));

double total = 0.0;
for (const Figura* f : figs) {
    std::cout << f->nombre() << ": " << f->area() << '\n';
    total += f->area();
}
std::cout << "total: " << total << '\n';

for (Figura* f : figs) delete f;   // usa ~Circulo y ~Rectangulo

La salida es Circulo: 3.14159, Rectangulo: 12 y total: 15.1416. El delete del final llega al destructor correcto porque ~Figura es virtual; sin esa palabra, AddressSanitizer reporta el error de tipo en la liberación.
