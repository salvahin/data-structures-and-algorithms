R12 · Punto de partida

Veintinueve líneas de error, una sola causa


#include <iostream>
class Pila {
    int datos[10];
    int cima;
public:
    Pila() : cima(0) {}
    void push(int v) { datos[cima++] = v;
    int pop() { return datos[--cima]; }
};
      

$ g++ -std=c++17 pila.cpp  2>&1 | wc -l
29

Falta una llave al final de la línea 7. El compilador produce cuatro errores, dos advertencias y tres notas, y ninguno de ellos dice "falta una llave en la línea 7".

R12 · Cómo leer la salida

Solo el primer error es información

El compilador lee tu archivo de arriba abajo. Cuando encuentra algo que no puede interpretar, hace una suposición y sigue, para reportar de una vez todo lo que pueda. Si la suposición es incorrecta, todo lo que lee después se interpreta mal.

  • Los errores posteriores describen el estado confundido del compilador, no tu programa.
  • El procedimiento es: leer el primer error, corregirlo, recompilar. Nunca corregir la lista completa de una pasada.
  • Para ver solo el principio: g++ archivo.cpp 2>&1 | head -20, o directamente g++ -fmax-errors=1 archivo.cpp.
Un error corregido puede eliminar cuarenta mensajes. Contar los mensajes no mide cuánto falta.
R12 · Cómo leer la salida

Las cuatro partes de un diagnóstico


e3.cpp:6:24: error: cannot convert 'std::string' to 'int'
    6 |     std::cout << doble(s) << '\n';
      |                        ^
e3.cpp:3:15: note:   initializing argument 1 of 'int doble(int)'
    3 | int doble(int n) { return 2 * n; }
      |           ~~~~^
  • e3.cpp:6:24 — archivo, línea y columna. La columna es donde el compilador se detuvo, que no siempre es donde está la falta.
  • error — la severidad. warning no detiene la compilación; note no es un problema aparte sino contexto del diagnóstico anterior.
  • El texto del mensaje, y debajo la línea de código con un cursor apuntando a la posición exacta.
Checkpoint

Compilas y g++ imprime 41 mensajes. ¿Cuál es el siguiente paso más eficiente?

B. A partir del primer error el compilador trabaja sobre una suposición que puede ser falsa, así que los 40 mensajes siguientes describen un programa que no escribiste. A invierte tiempo en información que probablemente desaparezca sola. C confunde el resumen final (ld returned 1 exit status, por ejemplo) con el diagnóstico útil.
R12 · Errores de sintaxis

El punto y coma que falta se reporta una línea después


#include <iostream>
class Punto {
    int x, y;
public:
    Punto(int a, int b) : x(a), y(b) {}
    int getX() const { return x; }
}

Punto origen(0, 0);
int suma(Punto a, Punto b) { return a.getX() + b.getX(); }
      

e5.cpp:9:7: error: expected initializer before 'origen'
e5.cpp:13:23: error: 'origen' was not declared in this scope

Sin el punto y coma, Punto y lo que sigue forman una sola declaración, así que el compilador espera un inicializador donde tú escribiste un nombre de variable. La falta está en la línea 7 y el mensaje habla de la 9. El segundo error es eco: origen no existe porque su declaración no llegó a formarse.

R12 · Errores de sintaxis

La llave faltante del arranque, mensaje por mensaje


pila.cpp:14:2: error: expected '}' at end of input
pila.cpp:2:12: note: to match this '{'
pila.cpp:8:12: warning: empty parentheses were disambiguated
               as a function declaration [-Wvexing-parse]
pila.cpp: In member function 'int Pila::main()':
pila.cpp:13:20: error: 'class Pila' has no member named 'pop'
pila.cpp:14:2: error: expected unqualified-id at end of input
  • La note de la línea 2 es la pista real: el compilador llegó al final del archivo buscando la llave que cierra class Pila.
  • In member function 'int Pila::main()' revela lo ocurrido: main quedó absorbido dentro de la clase.
  • Los tres mensajes restantes son consecuencias de esa absorción. Agregar la llave los borra todos.
Checkpoint

g++ reporta error: expected initializer before 'contador' en la línea 40, y esa línea es Registro contador;, que se ve correcta. ¿Dónde conviene buscar?

A. El compilador reporta dónde se dio cuenta, no dónde está la falta. expected initializer sobre una línea que se ve bien casi siempre significa que la construcción anterior no terminó. B toma la posición del cursor como si fuera infalible. C confunde etapas: si Registro no estuviera declarado, el mensaje sería 'Registro' was not declared in this scope, y sería del compilador, no del enlazador.
R12 · Dos etapas, dos programas

Quién firma el mensaje

CompiladorEnlazador
Formatoarchivo.cpp:12:5: error:/usr/bin/ld: … o collect2:
Qué veUna unidad de traducciónTodos los .o a la vez
Qué revisaSintaxis, tipos, nombres declaradosSímbolos: quién los define, quién los usa
Mensajesexpected, not declared, cannot convertundefined reference, multiple definition

Un mensaje del enlazador no menciona líneas ni columnas de tu código con la precisión del compilador, porque a esas alturas ya no hay código fuente: hay símbolos.

R12 · Errores de enlazado

undefined reference: alguien prometió y nadie entregó


/usr/bin/ld: main.o: in function `main':
main.cpp:(.text+0x3c): undefined reference to
                       `Cuenta::depositar(double)'
collect2: error: ld returned 1 exit status

El mensaje se lee de dentro hacia fuera: quién lo necesita (main.o, dentro de main) y qué le falta (el cuerpo de Cuenta::depositar(double)). Las causas posibles son pocas:

  • El método se declaró en el header y su cuerpo no se escribió en ningún .cpp.
  • El cuerpo existe pero el archivo que lo contiene no se pasó al comando de enlazado.
  • Las firmas no coinciden: falta el Clase::, sobra o falta un const, o un parámetro es int en un lado y double en el otro. El nombre entre comillas del mensaje trae la firma completa, así que compáralo con tu declaración carácter por carácter.
Checkpoint

El mensaje es multiple definition of `doble(int)', con first defined here apuntando a otro objeto. ¿Qué lo produce?

C. Cada unidad de traducción recibió su copia del cuerpo y generó su propio símbolo; el enlazador encontró dos y aplicó la regla de una definición por programa. La solución es dejar solo la declaración en el header, o marcar la función inline. A describe un efecto de la guarda que no aplica entre archivos distintos: la guarda actúa dentro de una unidad. B produce el mismo mensaje en casos concretos, pero el first defined here apuntaría al mismo archivo fuente, no a otro.
R12 · Aprovechar las notas

g++ suele decirte la solución en la línea siguiente


e4.cpp:3:10: error: 'vector' is not a member of 'std'
    3 |     std::vector<int> v;
      |          ^~~~~~
e4.cpp:2:1: note: 'std::vector' is defined in header '<vector>';
                  did you forget to '#include <vector>'?
    1 | #include <iostream>
  +++ |+#include <vector>
e4.cpp:3:17: error: expected primary-expression before 'int'
e4.cpp:4:5: error: 'v' was not declared in this scope

La nota trae el arreglo escrito, con +++ marcando la línea que hay que agregar. Los dos errores siguientes son eco del primero: sin el tipo, la variable no se declara, y sin la variable nada de lo que la use tiene sentido.

R12 · Plantillas

Ciento catorce líneas para un operador que falta


struct Punto { int x, y; };

std::vector<Punto> v{{3,1},{1,2}};
std::sort(v.begin(), v.end());
      

/usr/include/c++/11/bits/stl_algo.h:1904:34: required from
  '_RandomAccessIterator std::__unguarded_partition_pivot(…)
   [with _RandomAccessIterator = __gnu_cxx::__normal_iterator<…>]'
tpl.cpp:6:14:   required from here
predefined_ops.h:45:23: error: no match for 'operator<'
                        (operand types are 'Punto' and 'Punto')

Las decenas de líneas required from son la cadena de instanciación: cómo se llegó desde tu código hasta el interior de la biblioteca. Se leen dos líneas: la que dice required from here y menciona tu archivo, y la que empieza con error:. Aquí: Punto no tiene operator< y std::sort lo necesita.

Checkpoint

Ante un muro de 114 líneas generado por una plantilla, ¿qué buscas primero?

A. Esas dos líneas dan el punto de tu código que originó la instanciación y la razón concreta de la falla. B falla porque en las plantillas la salida arranca dentro de los headers del sistema, con rutas de /usr/include que no te sirven. C interpreta los nombres internos de la biblioteca como el problema; son solo los pasos intermedios de la instanciación.
R12 · Trampas comunes

Cuatro formas de leer mal un error

  • Editar las cuarenta líneas mencionadas en la salida. La mayoría desaparecen al corregir la primera.
  • Buscar la falta exactamente en la línea y columna que señala el cursor, sin mirar las líneas anteriores.
  • Ignorar las note por parecer secundarias. Suelen traer la declaración con la que el compilador estaba comparando, o el arreglo ya escrito.
  • Tratar un undefined reference como error de sintaxis y revisar el archivo que lo menciona, cuando lo que falta está en otro o directamente no está en el comando.
R12 · Ejercicio

Cinco mensajes, cinco diagnósticos

Para cada mensaje, di qué etapa lo emitió y qué hay que corregir. Sin ver el código.


1) p1.cpp:9:7: error: expected initializer before 'origen'
2) /usr/bin/ld: undefined reference to `Cuenta::depositar(double)'
3) p3.cpp:6:24: error: cannot convert 'std::string' to 'int'
4) p4.cpp:3:10: error: 'vector' is not a member of 'std'
5) /usr/bin/ld: multiple definition of `doble(int)'
  1. Compilador, sintaxis. Una declaración anterior no terminó: falta el punto y coma después de la llave que cierra una clase, arriba de la línea 9.
  2. Enlazador. El cuerpo de depositar no existe, o su .cpp no se pasó al comando, o la firma del .cpp no coincide con la del header.
  3. Compilador, tipos. Se llamó una función que espera int con un std::string. La note siguiente indica qué parámetro es.
  4. Compilador, nombre no declarado. Falta #include <vector>. Los errores posteriores sobre la variable son eco.
  5. Enlazador. El cuerpo de doble está en un header incluido por dos .cpp. Dejar la declaración en el header y el cuerpo en un .cpp, o marcarla inline.

Reproduce los cinco en tu computadora: escribe programas mínimos que provoquen cada mensaje y compáralos con la salida real de tu compilador.
