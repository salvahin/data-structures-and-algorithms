Qué es una prueba

Pruebas · La idea

Un programa que revisa a otro programa


LinkedList<int> l;
l.insert(10, 0);
l.insert(20, 1);

l.print();                  // 10 20   (una persona tiene que mirarlo)
if (l.size() != 2) cout << "FALLA: size" << endl;   // el programa lo revisa
  • Una prueba ejecuta el código con una entrada conocida y compara el resultado contra el que debería dar.
  • Si la comparación la hace el programa, la prueba se puede repetir después de cada cambio sin que nadie revise la salida a ojo.
Pruebas · Alcance

Qué demuestra una prueba que pasa

  • Que el código dio el resultado correcto para esa entrada.
  • Nada sobre las entradas que no se probaron. Una lista puede pasar cien pruebas con elementos en medio y fallar al borrar la cabeza.
  • Dijkstra lo dijo en 1969: probar puede mostrar que hay errores, no que no los hay.

Por eso la habilidad central es elegir los casos: pocas pruebas bien escogidas encuentran más errores que muchas pruebas parecidas.

assert en C++

assert · Uso

Detener el programa si una condición es falsa


#include <cassert>

int main() {
    LinkedList<int> l;
    l.insert(10, 0);
    assert(l.size() == 1);   // verdadero: no pasa nada y sigue
    assert(l.size() == 5);   // falso: el programa se detiene aqui
}
  • assert viene de <cassert> y recibe una condición, como un if.
  • Si la condición es verdadera, no hace nada. Si es falsa, imprime un mensaje y termina el programa en ese momento.
assert · Cuando falla

El mensaje dice dónde y qué


g++ -std=c++17 -Wall -g test_lista.cpp -o test_lista
./test_lista

test_lista: test_lista.cpp:7: int main(): Assertion `l.size() == 5' failed.
Aborted (core dumped)
Parte del mensajeQué te dice
test_lista.cpp:7Archivo y línea del assert que falló
int main()La función donde estaba

assert · Por dentro

assert es una macro


// assert(cond) equivale, aproximadamente, a esto:
if (!(cond)) {
    // imprime archivo, linea, funcion y el texto de cond
    abort();              // termina el programa
}
  • assert no es una función: es una macro. El preprocesador la reemplaza por ese if antes de compilar.
  • Por eso puede mostrar el texto de la condición y el número de línea: los toma del código fuente al momento de reemplazarla.
assert · NDEBUG

Con -DNDEBUG, los assert desaparecen


assert(l.remove(7));      // mal: con NDEBUG, remove ni siquiera se llama

bool ok = l.remove(7);    // bien: la operacion corre siempre
assert(ok);               // y solo la revision depende de NDEBUG
  • Al compilar con g++ -DNDEBUG, la macro se reemplaza por nada. Se usa en versiones finales para no pagar el costo de las revisiones.
  • Regla: dentro de un assert solo va una condición que lee el estado. Nada que lo modifique.
Checkpoint

Las pruebas pasan, pero al compilar con -DNDEBUG la lista termina con un elemento de más. El código tiene assert(l.insert(5, 0));. ¿Qué pasó?

C. La macro se reemplaza por nada, con todo lo que tenía adentro. Con las revisiones activas la lista tenía ese 5; sin ellas, no, y el resto del programa trabaja con otra lista. Es la razón de la regla: la operación se ejecuta fuera del assert y dentro solo se revisa su resultado.
assert · Dentro de la clase

Revisar el invariante desde la propia lista


void checarInvariante() {
    int n = 0;
    Nodo* actual = head;
    while (actual != nullptr) {     // el mismo recorrido de print()
        n++;
        actual = actual->next;
    }
    assert(n == count);             // count debe coincidir con los nodos
}
  • Se llama al final de insert y remove, o desde las pruebas. Si alguna operación olvidó actualizar count, el error aparece en ese momento.
  • assert es para errores del programador. Una posición inválida que manda el usuario se maneja con lo que diga el contrato: insert devuelve false.

Anatomía de una prueba

Pruebas · Anatomía

Preparar, actuar, verificar


void test_remove_cabeza() {
    LinkedList<int> l;              // preparar: una lista conocida
    l.insert(10, 0);
    l.insert(20, 1);

    bool ok = l.remove(10);         // actuar: una sola operacion

    assert(ok);                     // verificar todo lo que debio cambiar
    assert(l.size() == 1);
    assert(l.find(20) == 0);        // el 20 quedo como cabeza
}

remove puede devolver true y aun así dejar size mal o la cabeza sin actualizar. Se revisa el estado completo, no solo el valor de retorno.

Pruebas · Organización

Una función por caso, un nombre que lo explique


void test_lista_nueva_esta_vacia() { /* ... */ }
void test_insert_en_lista_vacia()  { /* ... */ }
void test_remove_cabeza()          { /* ... */ }

int main() {
    test_lista_nueva_esta_vacia();
    test_insert_en_lista_vacia();
    test_remove_cabeza();
    cout << "Todas las pruebas pasaron" << endl;
}
  • Si un assert falla, el mensaje trae el nombre de la función, que ya dice qué caso se rompió. Cada prueba crea su propia lista, así que no depende de las anteriores.

Pensar en los casos límite

Casos límite · Fronteras

Los errores viven en los bordes

insert(x, pos) sobre una lista con count = 3:

Cinco pruebas cubren las cinco zonas. Probar 1 y 2 a la vez no agrega nada: el código hace lo mismo con los dos.

Casos límite · Cómo encontrarlos

Las preguntas que hay que hacerle a cada operación

  • ¿Qué pasa si la lista está vacía?
  • ¿Y si tiene un solo elemento?
  • ¿Y si la operación toca el primero? ¿Y el último?
  • ¿Y si el valor no existe? ¿Y si está repetido?
  • ¿Y si la posición está fuera de rango?
  • Después de vaciar la lista, ¿se puede volver a usar?

Cada respuesta se busca en el contrato de la sesión 12. Si el contrato no la dice, falta una decisión de diseño.

Casos límite · De las preguntas a las pruebas

Los casos de remove(x)

CasoAntesLlamadaEsperado
Vacía[]remove(5)false, []
Único[7]remove(7)true, []
Cabeza[10, 20, 30]remove(10)true, [20, 30]
Último[10, 20, 30]remove(30)true, [10, 20]
No existe[10, 20]remove(99)false, [10, 20]
Repetido[5, 8, 5]remove(5)true, [8, 5]

Cada renglón se convierte en una función de prueba. El caso "en medio" casi no hace falta: es el que siempre se prueba primero.

Casos límite · Un error real

Un remove que olvidó la cabeza


bool remove(T x) {
    if (head == nullptr) return false;
    // falta: if (head->dato == x) { ... }
    Nodo* prev = head;
    while (prev->next != nullptr && prev->next->dato != x)
        prev = prev->next;
    if (prev->next == nullptr) return false;
    // ... re-enlazar, delete, count-- y return true, como en la sesion 12
}

Con este código, las pruebas de "en medio", "último", "no existe" y "vacía" pasan. El ciclo empieza comparando head->next, así que nunca revisa la cabeza.

Casos límite · Un error real

La prueba de la cabeza lo atrapa


void test_remove_cabeza() {
    LinkedList<int> l;
    l.insert(10, 0);
    l.insert(20, 1);
    bool ok = l.remove(10);
    assert(ok);
    assert(l.size() == 1);
}
      

test_lista: test_lista.cpp:6: void test_remove_cabeza(): Assertion `ok' failed.

El mensaje ya localiza el problema: la función test_remove_cabeza dice qué caso falló, y la línea 6 dice que remove devolvió false para un valor que sí estaba.

Checkpoint

Una suite tiene 12 pruebas: todas insertan entre 5 y 10 elementos en posiciones intermedias y buscan valores existentes. Todas pasan. ¿Qué se puede concluir?

B. Las 12 pruebas visitan la misma zona de casos. Los errores de una lista (perder head, no actualizar el último enlace, leer memoria liberada) aparecen en las fronteras que ninguna prueba toca. El número de pruebas no mide qué tan bien se cubren los casos.
Checkpoint

La lista tiene 4 elementos. ¿Qué conjunto de posiciones prueba mejor insert(x, pos)?

A. Con count = 4, las posiciones válidas van de 0 a 4. La A prueba una inválida a cada lado (-1 y 5), la cabeza (0), el final (4) y una en medio (2). La B solo prueba el medio. La C repite el caso "inválida por arriba" cuatro veces y nunca prueba el final.

Pruebas y memoria

Memoria · Lo que assert no ve

Pruebas que pasan con memoria rota


g++ -std=c++17 -g -fsanitize=address test_lista.cpp -o test_lista
./test_lista     # corre las mismas pruebas y vigila la memoria

valgrind --leak-check=full ./test_lista   # alternativa sin recompilar
  • Un assert revisa valores. Una fuga o un uso de memoria liberada pueden dejar todos los valores correctos.
  • Compilar las pruebas con AddressSanitizer agrega esa revisión sin escribir nada nuevo: si hay un error de memoria, el programa se detiene con un reporte.
  • Valgrind hace lo mismo sobre el ejecutable normal, más lento.
Memoria · Leer el reporte

Un reporte de ASan se lee de arriba hacia abajo


ERROR: AddressSanitizer: heap-use-after-free
  READ of size 8 at 0x602000000030
  #0 LinkedList<int>::remove(int)   linkedlist.hpp:41
  ...
freed by thread T0 here:
  #0 operator delete(void*)         linkedlist.hpp:39
  • Primera línea: el tipo de error. Después: dónde se usó la memoria inválida y dónde se había liberado.
  • Aquí la línea 41 leyó lo que la 39 acababa de liberar: el delete quedó antes de re-enlazar, el orden que vimos en la sesión 12.

Complejidad · El método

Medir, duplicar n, graficar


for (int n = 1000; n <= 1024000; n = n * 2) {
    LinkedList<int> l = construir(n);    // lista con n elementos

    auto inicio = chrono::steady_clock::now();
    int tam = l.size();                  // la operacion medida
    auto fin = chrono::steady_clock::now();

    auto ns = chrono::duration_cast<chrono::nanoseconds>(fin - inicio);
    cout << n << " " << ns.count() << " " << tam << endl;
}
  • Duplicar n hace legible la forma: O(1) no cambia, O(n) se duplica, O(n²) se cuadruplica.
  • Compilar con -O2 y repetir cada medición varias veces. Se imprime tam para que el compilador no elimine la llamada.

Por qué importa hoy

Revisar qué casos faltan en las pruebas

  • Un asistente de IA genera pruebas rápido, y suele producir diez variantes del caso que funciona y ninguna del caso que rompe.
  • Revisar esas pruebas es recorrer las preguntas de hoy (vacía, uno, primero, último, no existe, fuera de rango) y buscar cuál no está.
  • La misma revisión sirve para pruebas escritas por un compañero o por ti hace seis meses.
STL

std::vector como oráculo


LinkedList<int> lista;
vector<int> vec;

for (int i = 0; i < 10000; i++) {
    int x = rand() % 100;
    int pos = rand() % (vec.size() + 1);
    lista.insert(x, pos);
    vec.insert(vec.begin() + pos, x);
}
assert(lista.size() == (int) vec.size());
  • La misma secuencia corre sobre tu lista y sobre el contenedor estándar; con un get(pos) se compara elemento por elemento.
  • Prueba miles de casos al azar sin escribirlos a mano. Complementa la suite de casos límite; no la reemplaza.
