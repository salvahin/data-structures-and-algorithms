R15 · Base y derivada

La derivada contiene a la base


class Persona {                    // base
    std::string nombre_;
public:
    Persona(const std::string& n) : nombre_(n) {}
    std::string nombre() const { return nombre_; }
};

class Empleado : public Persona {  // derivada
    double sueldo_;                // + el constructor del slide 5
};

Empleado e("Ana", 1000);
e.nombre();      // método que Empleado no declaró

Un Empleado lleva dentro un subobjeto Persona completo, con sus campos y sus métodos, y añade sueldo_. Por eso e.nombre() funciona sin que Empleado escriba nada.

R15 · Constructores

La base se construye desde la lista de inicialización


class Empleado : public Persona {
    double sueldo_;
public:
    Empleado(const std::string& n, double s)
        : Persona(n),        // 1. el subobjeto base
          sueldo_(s) { }     // 2. los miembros propios
};
  • El nombre de la base va primero en la lista, antes que cualquier miembro. Es la única forma de pasarle argumentos.
  • Si omites Persona(n), el compilador intenta el constructor por omisión de la base. Cuando la base no lo tiene, sale el error del arranque.
  • El cuerpo del constructor derivado corre cuando la base ya está construida, así que ahí dentro puedes usar sus métodos.
Checkpoint

Base solo tiene Base(int). Escribes Derivada(int x) : campo_(x) { } y el compilador pide Base::Base(). ¿Cuál es el arreglo?

C. Sin una llamada explícita, el compilador usa el constructor por omisión de la base, que aquí no existe. Nombrarla en la lista de inicialización resuelve el error. La opción A llega tarde: para cuando el cuerpo se ejecuta la base ya tuvo que quedar construida. La B cambia la visibilidad de los campos y no aporta un constructor.
R15 · Acceso

protected: visible para las derivadas


class Persona {
private:
    int edad_ = 0;           // ni siquiera la derivada lo ve
protected:
    std::string nombre_;     // la derivada sí
};

class Empleado : public Persona {
public:
    void saludar() const {
        std::cout << "Soy " << nombre_ << '\n';  // compila
        // std::cout << edad_;                    // error: privado
    }
};

protected se comporta como private frente al código de fuera y como public frente a las clases derivadas. Cuando un método público de la base ya te da el dato, prefiérelo: protected ata las derivadas a los nombres de los campos y cambiarlos después rompe todas.

R15 · Orden de construcción

Se construye de arriba hacia abajo

Cada constructor corre con su base ya terminada, así que puede apoyarse en ella sin verificar nada.

R15 · Orden de destrucción

Se destruye en el orden inverso


int main() {
    std::cout << "--- inicio ---\n";
    { Gerente g("Ana", 1000, 5); }   // vive dentro del bloque
    std::cout << "--- fin ---\n";
}
      

--- inicio ---
Persona(Ana)   Empleado   Gerente
~Gerente       ~Empleado  ~Persona
--- fin ---

La salida real trae una línea por mensaje; aquí van agrupadas por fase. La destrucción invierte la construcción: primero ~Gerente, que libera lo que Gerente pidió, y al final ~Persona. Ninguna clase destruye recursos que otra todavía pueda estar usando.

Checkpoint

Con Persona → Empleado → Gerente, ¿qué imprime { Gerente g; } si cada constructor y cada destructor escriben su nombre?

A. La construcción va de la base a la derivada y la destrucción recorre el camino de regreso. La opción B invierte la construcción: el constructor de Gerente no puede empezar antes de que exista su parte Persona. La C construye bien pero destruye en el mismo orden, lo que dejaría a ~Gerente trabajando sobre una base ya destruida.
R15 · Qué se hereda

Tres cosas que no pasan a la derivada

Elemento¿Se hereda?Qué ocurre
Métodos y camposSíLa derivada los usa según su nivel de acceso
ConstructoresNoLa derivada escribe los suyos y llama a los de la base
DestructorNoEl de la base se ejecuta siempre, al final
operator= y friendNoLa amistad no se transfiere; operator= se redefine si hace falta

La derivada sí puede reutilizar el operator= de la base llamándolo por su nombre: Persona::operator=(otro); dentro del suyo.

R15 · Herencia o composición

Heredar o contener


class Auto : public Motor { };   // "un auto es un motor": falso
class Auto { Motor motor_; };    // "un auto tiene un motor"

// heredar: Pila queda con toda la interfaz de vector
class Pila : public std::vector<int> { };  // insert(), erase()

// contener: Pila expone solo lo suyo
class Pila {
    std::vector<int> datos_;
public:
    void push(int x) { datos_.push_back(x); }
    int tope() const { return datos_.back(); }
};

Con composición, Pila decide qué operaciones ofrece. Heredando de std::vector, cualquiera puede llamar insert() en medio y romper el orden de entrada y salida que la pila promete.

R15 · Criterio

Cuándo no heredar

  • Cuando la frase "un X es un Y" no se sostiene en todos los lugares donde se usa Y. La conversión implícita a la base permite que una derivada aparezca donde se espera la base, así que el compromiso vale para toda la interfaz.
  • Cuando solo quieres tres métodos de la otra clase. Contén un objeto y expón esos tres; lo demás queda fuera del alcance de quien use tu clase.
  • Cuando la base tiene invariantes que la derivada puede violar sin darse cuenta, como el orden interno de un contenedor.
La pregunta que decide: ¿el código que recibe una Base& puede trabajar con tu derivada sin enterarse de la diferencia?
Checkpoint

Necesitas una clase Bitacora que guarde mensajes y ya tienes ListaEnlazada con insertar y recorrer. ¿Qué conviene?

B. Una bitácora no es una lista enlazada: usa una para almacenar. Con composición la lista queda como detalle interno y puedes cambiarla por un vector sin tocar a nadie. La opción A hereda para reutilizar código, que es la trampa de esta sesión: expone toda la interfaz de la lista a quien use la bitácora. La C intenta tapar el problema, y de paso deja de cumplirse "una bitácora es una lista", con lo que la herencia ya no tiene sentido.
R15 · Trampas comunes

Tres formas de complicarse con la herencia

  • Heredar para no repetir código. La herencia establece que la derivada sirve en todo contexto donde sirva la base; reutilizar el cuerpo de dos métodos no requiere ese compromiso.
  • Olvidar la llamada al constructor base y recibir un error que menciona un constructor que nunca escribiste.
  • Poner todos los campos en protected por si acaso. Cada campo protegido es un nombre que las derivadas van a usar y que ya no puedes renombrar ni quitar.
R15 · Ejercicio

Rastrea el orden en tres niveles

  1. Escribe Persona, Empleado : public Persona y Gerente : public Empleado, cada una con un campo propio.
  2. Pon un std::cout en cada constructor y en cada destructor con el nombre de la clase.
  3. Antes de compilar, escribe en papel la salida de { Gerente g("Ana", 1000, 5); }. Después compílalo y compara.

--- inicio ---
Persona(Ana)
Empleado
Gerente
~Gerente
~Empleado
~Persona
--- fin ---

Los tres constructores terminan antes de que el objeto exista para el resto del programa, y los tres destructores corren al cerrar la llave, en orden inverso. Ese orden es el mismo que verás en R16 cuando el destructor sea virtual.
